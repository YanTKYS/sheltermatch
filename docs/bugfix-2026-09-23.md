# バグ修正・リファクタリング記録（2026-09-23）

`sheltermatch.ipynb` / `address_geocode.ipynb` / `src/review/` について、**職員が通常の業務範囲で
使ったときに支障となる不具合**を洗い出して修正し、あわせて読みづらい箇所を整理した記録
（前回分: [docs/bugfix-2026-09-22.md](./bugfix-2026-09-22.md)）。

通常業務では起こり得ない異常値（あり得ない桁数、特殊な文字コードの混入等）への対応は、
今回も対象外としている。

出力仕様（結果CSVの列構成・値）は変更していない。修正前後で同じ入力から出力した
`assigned_shelters.csv` がバイト単位で一致することを、通常ケース・ハザードなし・`TOP_N=8`・
1000件・前回の結果CSVの再投入の5パターンで確認している。レビューHTMLへ埋め込むデータも、
背景地図情報の持ち方（下記 2-2）を除いて一致している。

## 1. 修正した不具合

### 1-1. 要支援者CSVの差し替えに失敗したあと先へ進むと、別人の避難所候補が付いた結果CSVが出ていた

**今回いちばん影響が大きい不具合。**

一度最後まで実行したあと、別の要支援者CSVを「要支援者CSV読込・入力チェック」セルで
アップロードし直し、そのCSVが入力チェック（`resident_id` の重複・空欄、列不足）で止まった
とする。この状態で後続のセルを実行すると、次のことが起きていた。

- 要支援者の行（`resident_id`・住所）は **今回の** CSVのもの
- 座標・避難所候補・距離は **前回の** CSVの同じ行位置の人のもの

つまり、**ある要支援者の行に、別人の座標と避難所候補が付いた `assigned_shelters.csv`** が
作られ、ダウンロードされていた（件数が違えば行が欠けたり空行が付いたりする）。
レビューHTMLは件数の食い違いで止まることがあるが、結果CSVはその前にダウンロード済みだった。

再現（修正前）: 100件のCSVで一通り実行 → `resident_id` が重複した60件のCSVをアップロード
（入力チェックで停止）→ 候補算出セル・出力セルを実行

| resident_id（今回のCSV） | latitude | 候補1 | 距離 |
| --- | --- | --- | --- |
| P0201 | 26.107621 | 避難所24 | 311.1 m ← 前回のP0001の候補 |
| P0201 | 26.119895 | 避難所27 | 1405.5 m ← 前回のP0002の候補 |

修正後は、読込セルの冒頭で前回の要支援者データを消し、入力チェックをすべて通ったときだけ
要支援者の行と座標を同時に更新するようにした。候補算出セルは、要支援者データが無ければ
「要支援者一覧CSVが読み込まれていません」と表示して止まる。

同じ考え方で、次の4つも直した。

- **ハザードデータ**: 読み直しに失敗したあと先へ進むと、前回読み込んだハザードデータのまま
  黙って判定していた。読込セルの冒頭で前回のデータを消すようにし、既存の
  「ハザードデータが読み込まれていません」の確認で止まるようにした
- **避難所一覧**: 読み直しに失敗したあと先へ進むと、前回の避難所一覧のまま候補を算出していた
  （有効な避難所が0件で止まった場合は、全員「候補なし」の結果CSVが作られていた）。
  要支援者CSVと同じく、最後まで読み込めたときだけ更新するようにした
- **出力セル**: 設定・入力を変えたあと（読込に成功した場合も含む）、候補算出セルを飛ばしたり
  候補算出セルが止まったりしたまま出力セルを実行すると、前回の結果CSVを今回の結果のように
  再出力していた。結果に影響するセル（利用者設定・要支援者CSV読込・避難所取得・ハザードデータ
  読込・候補算出）の冒頭で前回の算出結果（`final_df` / `review_rows`）を消すようにした。
  出力セルでも最後の安全策として、算出結果・要支援者データ・避難所データ・（判定する設定なら）
  ハザードデータがそろっていることを確認し、そろっていなければ出力しない
- **ハザード判定の設定切替**: `ENABLE_HAZARD_CHECK=True` で一度実行したあと `False` に変えて
  再計算すると、結果CSVはハザード判定なしなのに、レビューHTMLには前回読み込んだハザード区域が
  表示されていた（ランタイムに残っていたハザードデータがそのまま渡っていた）。設定が `False` の
  ときはレビューHTML生成へハザードデータを渡さないようにした

いずれも、エラーが出たあとに職員が後続のセルを実行した場合や、途中のセルを飛ばして実行した
場合に起きる。「ランタイム → すべてのセルを実行」ではエラーの時点で止まるため起きない。

### 1-2. レビュー画面の地図が際限なく拡大・縮小でき、何も映らない状態になっていた

`review.html` の地図には拡大・縮小の上限が設定されていなかった。背景地図を画像として同梱して
いるため地図ライブラリが上限を自動で決められず、「＋」ボタンやマウスホイールで拡大を続けると
背景地図の1画素が画面いっぱいに引き伸ばされ、マーカー・直線もすべて画面外へ外れて何も
映らなくなり、どこを見ているのか分からなくなっていた（「＋」ボタンも押せるまま）。
縮小側も同様に、世界全体まで縮小できた。

ヘッドレスブラウザ（Chromium）で確認した結果:

| 操作 | 修正前 | 修正後 |
| --- | --- | --- |
| 「＋」を押し続ける | 止まらない。表示範囲の緯度・経度が小数4桁で同じ値になり、何も映らない | ズーム18で止まり「＋」が押せなくなる |
| ホイールで縮小し続ける | 世界全体まで縮小できる | ズーム10（沖縄本島中南部が見える程度）で止まる |

拡大はズーム18（建物が判別できる程度）、縮小はズーム10までに制限した。

### 1-3. ハザード判定をしたのに「ハザード判定を行っていない」と表示されることがあった

ハザードデータを読み込んで判定したものの、そのハザード区域が地図の表示範囲（要支援者・避難所の
周辺）に1件も無い場合、レビュー用HTML作成時に
「ハザード判定を行っていないため、ハザード表示用PNGは作成していません。」と表示されていた。
判定そのものは行われているため、「地図の表示範囲にハザード区域が無いため、ハザード表示用PNGは
作成していません。」と正しく表示するようにした（結果CSVの判定結果は元から正しい）。

## 2. リファクタリング（動作は変えていない）

### 2-1. 座標の有効性を二重に判定していた箇所を一本化した（`sheltermatch.ipynb`）

座標が使えるかどうかを、読込時の `match_status`（`ok` / `no_coordinates` / `invalid_coordinates`）
と、距離計算・ハザード判定の各関数の中の `is_valid_coordinate()` の2か所で別々に判定していた。
候補算出のループで `match_status` が `ok` の人だけ計算する形へ揃え、関数側の判定と
`is_valid_coordinate()` を削除した。判定の基準は同じ（空欄・数値でない・範囲外は対象外）。

あわせて、常に存在する列の有無を確認していた分岐（`build_shelter_records()` の
`_disaster_support` 列）、同じ結果になる条件分岐（レビュー用の `disaster_support`）、
戻り値を使わない確認関数（`ensure_coordinate_columns()` / `ensure_resident_columns()`）を整理した。

### 2-2. 背景地図の生成処理を1枚分の素直な処理にした（`src/review/review_builder.py`）

以前は広域図と詳細図の2枚を作っていた名残で、1枚しか作らない現在も「設定のリスト」
「リストを回すループ」「同じタイルを2回取らないためのキャッシュ」が残っていた。
1枚の背景地図を作る関数と3つの定数（ファイル名・ズーム候補・タイル数上限）に置き換えた。
生成される画像・表示範囲は変わらない。レビューHTMLへ埋め込むデータは
`basemap.detail.image` → `basemap.image` のように1段浅くなった（`review_template.html` も同時に修正）。

### 2-3. レビュー画面のJavaScriptを整理した（`src/review/review_template.html`）

- 起こらない失敗に備えた分岐を削除した（背景地図データが無い場合の分岐、ハザード画像レイヤーの
  作成を囲んでいた `try`、地図ライブラリの古い版向けの確認）。同梱ファイルが無い場合の
  案内表示（地図ライブラリ・背景地図画像）は、実際に起こり得るため残している
- 経緯度グリッドを、拡大縮小のたびに2回描き直していたのを1回にした
- どの要素でも作れるのに `createRow` という名前だった関数を `createElement` へ改名した

### 2-4. 文字コード判定の到達しない3段目を削除した（両Notebook）

CSVの文字コード判定は「UTF-8（BOM付き）→ CP932 → UTF-8」の順だったが、BOM付きUTF-8用の
読み方（`utf-8-sig`）はBOMの無いUTF-8もそのまま読めるため、3段目のUTF-8に進むことはなかった。
「UTF-8 → CP932」の2段にした。読み込めるファイルは変わらない（画面表示は
「UTF-8 (BOM付き) として読み込みました」→「UTF-8 として読み込みました」）。

`address_geocode.ipynb` では、中身が同じだった `REQUIRED_COLUMNS` と `OUTPUT_COLUMNS` を
`RESIDENT_COLUMNS` 1つにまとめた。

## 3. 確認方法

Google Colabの `google.colab.files`（アップロード・ダウンロード）、BODIK Data API、
地理院タイル、地図ライブラリの取得をモック化し、Notebookのセルを新規プロセスで順に通し実行して
確認した（実際のGoogle Colabでの確認は、この環境からは接続できないため未実施）。

- `sheltermatch.ipynb`: 通常ケース（ハザードあり）/ ハザードなし / `TOP_N=8`（避難所5件）/
  1000件 / 前回の結果CSVの再投入 / CP932で保存した要支援者CSV / 表示範囲外のハザードデータ。
  修正前後で結果CSVがバイト単位で一致することを確認
- `sheltermatch.ipynb` の再実行（いずれも一度正常に最後まで実行したあとに操作）:
  - 要支援者CSV・避難所一覧・ハザードデータのそれぞれで読み直しに失敗 → 候補算出セル・出力セルを
    実行し、どちらも止まり結果CSVが出力されないことを確認
  - 同じ4通り（不正な要支援者CSV / 正常な別の要支援者CSV / 不正な避難所CSV / ハザード読込失敗）と
    利用者設定の再実行について、**候補算出セルを飛ばして直接出力セルを実行** し、前回の
    `assigned_shelters.csv` がダウンロードされないことを確認
  - 正常な別の要支援者CSVへ差し替え → 候補算出セル → 出力セルの順に実行すれば、従来どおり
    新しい結果が出力されることを確認
  - `ENABLE_HAZARD_CHECK=True` で実行したあと `False` に変えて再計算し、レビューZIPにハザードPNG・
    ハザードレイヤーが含まれないことを確認（修正前は前回の津波レイヤーが残っていた）
- `address_geocode.ipynb`: 架空ABRマスター（ZIP 3種類）とCP932で保存した住所CSVで通し実行し、
  出力CSVをそのまま `sheltermatch.ipynb` へ投入できることを確認
- `review.html`: ヘッドレスChromiumで実際に開き、拡大・縮小の上限、検索、51人目以降への移動、
  候補行のクリック、レイヤー操作、背景地図の切替、assetsフォルダが無い場合の案内表示を確認
  （JavaScriptエラーなし）
- 住所変換の回帰テスト（`python3 -m unittest discover -s test`）: 18件すべて成功
