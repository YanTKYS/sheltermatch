# バグ修正・リファクタリング記録（2026-09-21）

`sheltermatch.ipynb` / `address_geocode.ipynb` について、**職員が通常の業務範囲で使ったときに
支障となる不具合**を洗い出して修正し、あわせて読みづらい箇所を整理した記録。

通常業務では起こり得ない異常値（あり得ない桁数、特殊な文字コードの混入等）への対応は、
今回の対象外としている。

## 1. 修正した不具合

修正前の動作は、いずれもローカル環境で実際に再現させたうえで直している。

### 1-1. 住所「673番地2」が別の地番へ変換されていた（address_geocode.ipynb）

**最も影響が大きい不具合。**

地番を取り出す処理が「番地」「番」を区切りではなく削除していたため、`673番地2` / `673番2` が
`6732` として解釈されていた。

- 該当する地番が無ければ `parcel_not_found`
- **たまたま `6732` という地番が存在すると、まったく別の場所の座標が `matched` として出力される**

「○○番地△」は日常的に使われる表記であり、しかも結果が `matched` になるため、職員が出力CSVを
見ても誤りに気付けなかった。

再現確認（架空のABRマスターによる検証）:

| 入力住所 | 修正前 | 修正後 |
| --- | --- | --- |
| `糸満市字糸満673番地2` | 地番`6732`の座標を`matched`として出力 | 地番`673-2`の座標を出力 |
| `糸満市字糸満６７３番地の２` | 地番`673-2`（正しい） | 変わらず正しい |
| `糸満市字糸満673` | 地番`673`（正しい） | 変わらず正しい |

「番地の」「番の」「番地」「番」「号」「の」をすべて区切り文字として扱うよう統一した。
数字として解釈できない場合に推測せず `parcel_not_found` とする方針は変えていない。

### 1-2. 座標欄に文字が入っている行が「空欄」と報告されていた（sheltermatch.ipynb）

`latitude` に「不明」等の文字が入っている行が、数値化に失敗した時点で欠損値と同じ扱いになり、
`match_status` が `invalid_coordinates` ではなく `no_coordinates`（＝座標欄が空欄）と
報告されていた。さらに、その値が結果CSVでは空欄に書き換えられて出力されるため、職員がCSVを見ても
「もともと空欄だったのか、何か書いてあったのか」が分からなかった。

- 空欄（`no_coordinates`）と、値は入っているが使えない（`invalid_coordinates`）を区別するよう修正
- 入力した `latitude` / `longitude` を書き換えず、そのまま結果CSVへ残すよう修正

### 1-3. ハザードデータ未読込のまま実行すると、全行が「区域外」と出力されていた

ハザードデータ読込セルでエラーが出た（ファイルを選ばなかった、対象外の形式だった等）あとに
候補算出セルを実行すると、ハザード判定の全列が `False` で出力されていた。

`False` はNotebookの説明上「有効な座標で判定した結果、ハザード区域外」を意味するため、
**実際には何も判定していないのに「安全」と読める結果CSV** が作られてしまう状態だった。

候補算出セルの冒頭で、ハザードデータが読み込まれていない場合は処理を止めるよう修正した
（ハザードデータの一部が読めなかった場合に処理を止める既存のfail-closed方針と揃えた）。

### 1-4. 前回の結果CSVを再投入すると、原因の分からないエラーで落ちていた

出力された `assigned_shelters.csv` は共通住民CSVの5列を含むため、そのまま入力として
受け付けられる。しかし `match_status` や `candidate_1` 等の列が二重になり、
`TypeError: int() argument must be ... not 'Series'` という、操作からは原因の推測できない
エラーで停止していた。

このNotebookが作る列は入力側から取り除いてから結合するよう修正し、置き換えたことを
画面に表示するようにした。

取り除く対象は、このNotebookが作る次の列名と完全に一致するものだけに限定している。

```text
match_status
resident_in_hazard
resident_hazard_types
candidate_N
distance_N_m
candidate_N_disaster_support
candidate_N_shelter_in_hazard
candidate_N_shelter_hazard_types
candidate_N_straight_line_intersects_hazard
candidate_N_straight_line_hazard_types
```

職員が結果CSVへ独自に追加した `candidate_1_note` / `candidate_1_確認結果` / `candidate_2_備考`
のような列は、名前が似ていても取り除かない（入力されたデータを黙って消さないため）。
`candidate_N` は、前回と異なる `TOP_N` で再実行された場合にも前回分の候補列が残らないよう、
今回の `TOP_N` に限定せず数字として判定している。

> **補足**: レビュー指摘により、当初の `candidate_\d+.*` という包括的な判定を、上記の
> 列名の厳密な一致へ改めた。包括的な判定では `candidate_1_note` 等が黙って削除されていた。

### 1-5. データ行が0件のCSVで、原因の分からないエラーで落ちていた

見出し行だけのCSVをアップロードすると `KeyError: "['match_status'] not in index"` で
停止していた。両Notebookとも、「データ行が1件もありません」と表示して止めるようにした。

### 1-6. 読み込めなかったハザードポリゴンが、何も表示されずに除外されていた

空・自己交差等で有効なジオメトリとして扱えなかったポリゴンは、件数も表示されずに除外されていた。
除外された区域はハザード判定に含まれないため、件数を表示するようにした
（除外する動作自体は変えていない）。

## 2. 処理時間（ハザード判定の待ち時間）

ハザード判定は、1回の判定ごとに約106,000件のポリゴンを全件調べていたため、要支援者数に比例して
待ち時間が延びていた（[docs/performance-test.md](./performance-test.md) の「7. ボトルネック」で
指摘済み）。

- GeoPandasの空間インデックス（`sindex`）で、交差し得るポリゴンだけに絞ってから判定するようにした
- 候補避難所は要支援者ごとに同じ避難所がくり返し選ばれるため、避難所地点の判定は避難所ごとに
  1回だけ行い、結果を使い回すようにした
- 避難所一覧を要支援者1人ごとにDataFrameから1行ずつ取り出し直していたのをやめ、最初に1回だけ
  取り出して使い回すようにした

実測（サンドボックス内ローカル実行・106,000ポリゴンの代用ハザードデータ・避難所55件相当。
実測環境の条件は performance-test.md の「0. 実測環境について」と同じ制約がある）:

| 要支援者数 | 修正前（候補算出＋ハザード判定） | 修正後 |
| --- | --- | --- |
| 100件 | 2.91秒 | 0.59秒 |
| 500件 | 15.08秒 | 2.95秒 |
| 1000件 | 31.68秒 | 6.37秒 |

判定結果が変わっていないことは、同じ入力・同じハザードデータで修正前後の出力CSVを比較し、
500件×全列がすべて一致することで確認した。

## 3. リファクタリング（動作は変えていない）

* 座標の読み取り・状態判定を `read_coordinates()` 1か所にまとめ、要支援者・避難所の両方で使う
  ようにした（以前は列を数値化する処理と、行ごとに状態を決める処理が別々の場所にあった）
* 避難所データの `shelters_raw` / `shelters` / `shelters_valid` の3つを、`shelters` /
  `shelters_valid` の2つに整理した
* ほぼ同じ内容だったハザード判定の2関数（地点・直線）を、共通の
  `hazard_types_intersecting()` と、座標チェックだけを行う薄い2関数に分けた
* コード値を対応表のキーへ揃える処理が避難所側とハザード側に二重にあったため、
  `normalize_code_value()` 1つにまとめた（災害種別の `"1"` / `"1.0"` の二重定義も解消）
* 候補列を組み立てるループにあった、候補がある場合と無い場合の重複した代入を整理した
* `address_geocode.ipynb` にあった文字コード判定の同じ処理2か所を `read_csv_auto()` にまとめた

## 4. 今回対応していないこと
