# sheltermatch 現状整理・開発方針

更新日: 2026-09-24

## 1. この文書の目的

`sheltermatch` が **今どうなっているか**（完成範囲・実装済みの仕様・確認の状況）と、**今後どう判断するか**
（優先順位・開発上のガードレール）をまとめる。

個別機能で技術的な問題が発生した場合でも、その問題だけを理由として本来の目的や優先順位を変更しないための
開発上のガードレールとして扱う。特に、補助機能で問題が発生したことを理由に、本体機能まで「難しいので後回し」
「PoCなので不要」などと再解釈しない。

変更の経緯・実装の細部は [CHANGELOG.md](../CHANGELOG.md) と各確認記録（下記「10. 関連ドキュメント」）に
任せ、この文書には現在の仕様と判断基準を書く。

---

## 2. sheltermatch の目的

要支援者ごとに、避難所候補を機械的に最終決定するものではない。

以下の情報を整理し、職員が避難先を判断するための一次資料を作成することを目的とする。

1. 要支援者の位置
2. 避難所の位置
3. 距離が近い避難所候補
4. 避難所の災害種別対応情報
5. 要支援者・候補避難所・両者を結ぶ直線とハザード区域との位置関係

このほか、レビュー用HTMLでは任意で「道路に沿った参考経路」を確認できる（下記「6.2」）。これは職員の
目視確認を助ける参考情報であり、上記の一次資料の内容（候補・順位・判定）を変えるものではない。

最終的な避難所の決定は職員が行う。

## 3. 完成範囲の整理

sheltermatch本体の主要機能は、完成しているものとして扱う。

本体の目的は、**要支援者ごとに、職員が避難先を判断するために必要な候補・距離・避難所の災害対応情報・
ハザード情報を整理して提示すること** である。正式なデータ成果物は `assigned_shelters.csv` である。

以下は、本体の完成条件には含めない。ただし「完成条件に含めない」ことは「実装しない・不要」という意味では
なく、本体の完成をこれらに依存させないという整理である。実装済みのものは、そのまま維持する。

| 項目 | 現在の状態 | 本体の完成条件との関係 |
| --- | --- | --- |
| 住所→座標変換 | 本体の前処理として、独立Notebook `address_geocode.ipynb` で実装済み（地番住所）| 含めない（緯度・経度入りのCSVで本体が完走できる）|
| 道路ネットワークによる経路探索 | レビューHTMLの任意の参考機能「道路に沿った参考経路」として実装済み（既定OFF）| 含めない（候補算出・正式成果物の完成条件ではない）|
| 安全経路の自動判定 | 実装していない。道路経路を安全な避難経路とは扱わない | 含めない |
| ハザードによる候補の自動除外 | 行わない | 含めない（引き続き行わない方針）|
| 独自の危険度スコア | 作らない | 含めない（引き続き作らない方針）|
| KML対応 | 実装していない | 含めない（必要性が確認できた場合に検討）|

## 4. 本体として完成させる機能

### 4.1 要支援者データの読込

要支援者一覧CSV（`resident_id,address,latitude,longitude,geocode_status` の5列）を読み込む。

座標が欠損している行や不正な行も削除せず、入力した値も書き換えずに処理結果へ残す。座標が利用できない場合は
候補計算を行わず、`match_status`（`no_coordinates` / `invalid_coordinates`）で状態を明示する。

### 4.2 避難所データの取得

避難所一覧は、原則としてBODIK Data APIから糸満市の自治体標準オープンデータセットを取得する。
API取得に失敗した場合はCSVアップロードへフォールバックできる。

自治体標準ODSの名称・緯度・経度・災害種別を利用する。災害種別は `1` = 対応済み / `2` = 2階以上であれば
対応済み / 空欄 = 未対応 を区別して保持する。これは避難所そのものの指定状況であり、GeoJSON / Shapefileに
よるハザード区域判定とは別の情報として扱う。

### 4.3 避難所候補の算出

要支援者と各避難所の座標から `geopy.distance.geodesic` により直線距離を計算し、既定では距離が近い上位3件
（`TOP_N`）を候補として出力する。これは道路距離・避難経路ではない。

**候補順位は直線距離だけで決める。** 以下によって自動変更しない。

* 避難所の災害種別対応
* ハザード区域判定
* 道路に沿った参考経路の距離（道路上の距離）
* その他の独自スコア

これらは職員判断のための別情報として出力・表示する。

### 4.4 ハザード区域判定

ハザード区域判定は **sheltermatch本体の完成対象** である。

実行時には `ENABLE_HAZARD_CHECK` によって使用するか選択できるが、これは利用時の任意設定であり、開発上の
優先度が低いことを意味しない。

読み込んだGeoJSON / ShapefileをEPSG:4326のPolygon / MultiPolygonとして統合し、以下を判定する。

* **要支援者地点**: ハザード区域の内部または境界上にあるか
* **候補避難所地点**: ハザード区域の内部または境界上にあるか
* **要支援者と候補避難所を結ぶ直線**: 単純な `LineString` がハザード区域と交差するか

直線の判定は **道路上の避難経路の安全性判定ではない**。「道路に沿った参考経路」とハザード区域との交差も
判定していない。「安全な避難経路」とは表現しない。

有効なPolygon / MultiPolygonは一切変更せずそのまま使う。公式配布データに実際に含まれている `is_valid=False`
のPolygon / MultiPolygon（自己交差等）は `shapely.make_valid()` で直してから使う（GeometryCollectionに
なる場合はPolygon / MultiPolygon成分だけを使い、区域として使える形にならなかったものは判定対象外とする）。
空・欠損のジオメトリ、Polygon / MultiPolygon以外のジオメトリは判定対象外とする。直した行も元の
`hazard_type` をそのまま引き継ぎ、種別・カテゴリを再解釈しない。

対応対象としているハザード種別と、その詳細区分の保持状況は以下のとおり。

* 洪水（国土数値情報A31a）: ZIP内部のサブフォルダをカテゴリとして保持する（実データで確認済みのカテゴリは
  `10_計画規模` / `20_想定最大規模` / `30_浸水継続時間` / `41_家屋倒壊等氾濫想定区域_氾濫流` /
  `42_家屋倒壊等氾濫想定区域_河岸侵食`）
* 土砂災害（国土数値情報A33）: ファイル名から入力なしで自動判定し、公式属性 `A33_001`（現象の種類）/
  `A33_002`（区域区分）から `急傾斜地の崩壊` / `土石流` / `地滑り` と、`土砂災害警戒区域(指定済)` /
  `土砂災害特別警戒区域(指定済)` 等の詳細区分をそのまま保持する
* 津波（沖縄県LEVEL1〜7）: 実データの `分類` 属性（例: `0.01m以上0.3m未満`）を保持する
* 高潮（沖縄県）: ファイル名からカテゴリ（`最大浸水深` / `浸水継続時間`）を保持する

複数種類に該当する場合は、該当種別をすべて保持する。ハザード判定結果による候補の自動除外・自動順位変更は
行わない。

詳細なデータ取得・利用手順は [docs/hazard-data.md](./hazard-data.md) を参照。

## 5. 住所→座標変換の位置付け

住所→座標変換は **sheltermatch本体処理の前処理** であり、独立Notebook `address_geocode.ipynb` として
実装済みである（本体へは統合しない）。本体の完成は、この機能に依存させない。緯度・経度があらかじめ用意された
要支援者データで、候補算出・災害種別情報・ハザード判定・結果CSV出力まで完走できる。

### 現在の方式: ABR公式CSVの手動取得・直接照合

* 公式ABR CSV3種類（町字マスタ・地番マスタ・地番位置参照）を利用者が手動アップロードし、対象自治体の
  データを抽出・結合して、pandasで直接照合する（自動ダウンロードは行わない）
* 出力CSVは本体の要支援者CSVと同じ5列で、そのまま本体へ投入できる
* ABRマスター準備と住所CSV変換を分離しており、同じColabランタイムの間は、住所CSVを差し替えるたびに
  ABR ZIPを再アップロードする必要はない
* 住居表示住所（`rsdt_addr_flg=1`の町字）は、現在の3データだけでは正しく座標化できるとは限らないため、
  `residential_display_area` として地番確定を明示的に保留し、無理に座標化しない
* 曖昧な住所を推測して `matched` 扱いにしない

住所表記の揺れ（全角／半角、漢数字の丁目、ハイフン類、空白、「字」「大字」の有無、`番地`/`番`/`号`/`の`
の表記差）への対応と、別の住所を同一視していないことは `test/test_address_conversion.py` で回帰テストしている。

### この方式を選んだ理由（判断根拠）

JageocoderとABR Geocoder（`@digital-go-jp/abr-geocoder`、および `abrdb`/`abrg` 構成）は、いずれも辞書・
キャッシュ生成のために配布データを自動ダウンロードする構成で、Google Colab・GitHub-hosted runner等の
クラウド環境から配布データを取得する段階で403等のエラーが発生した（ABR Geocoder公式リポジトリでも既知の
外部要因として報告されている。Jageocoderには加えてPython・converter APIの互換性問題もあった）。
そのため、利用者がABR公式CSVを手動取得して直接照合する方式（`experiments/abr_csv_geocode_poc.ipynb` で検証）
を採用した。検証の記録は `experiments/` に残している。

住居表示住所への対応や他自治体への展開は、必要になった場合に追加データ・追加検証を検討する。

データ取得元・利用手順・`geocode_status` の詳細は [docs/address-data.md](./address-data.md) を参照。

## 6. 現時点で実装済みの主要機能

### 6.1 Notebook本体（`sheltermatch.ipynb`）

* 要支援者CSV読込（UTF-8 / CP932の自動判定、5列・`resident_id` の空欄・重複チェック）
* 座標の欠損（`no_coordinates`）と、値はあるが使えない（`invalid_coordinates`）の区別。該当行も削除せず、
  入力値を書き換えずに結果へ保持
* BODIK Data APIからの避難所取得、API失敗時のCSVフォールバック、自治体標準ODS列名の正規化、
  災害種別対応情報の保持
* geodesicによる直線距離計算と上位 `TOP_N` 候補の算出
* ハザードデータの読込（GeoJSON単体、GeoJSON / Shapefileを含むZIP。展開・変換不要。大文字の拡張子、
  ZIP内パストラバーサル対策、CP932ファイル名の文字化け復元、CRSのWGS84統一、不正Polygonの修復）と、
  洪水・土砂災害・津波・高潮の種別・詳細区分の自動判定
* 要支援者地点・候補避難所地点・両者を結ぶ直線のハザード判定（空間インデックスで絞り込んでから判定）
* UTF-8 BOM付き結果CSV（`assigned_shelters.csv`）の出力
* 道路に沿った参考経路の算出（任意。下記「6.2」）
* レビュー用HTML（`sheltermatch_review.zip`）の出力（下記「6.3」）
* 誤った結果を出さないための停止・無効化: ハザードデータ未読込のまま候補算出セルを実行した場合の停止、
  入力の読み直しに失敗した場合や設定・入力のセルを再実行した場合の前回結果の無効化、
  前回の結果CSVを再投入した場合の結果列の置き換え

結果CSVの出力セルは、道路経路の算出・レビューHTMLの出力より前にある。道路データの取得やレビューHTMLの作成に
失敗しても、正式成果物である結果CSVは失われない。

### 6.2 道路に沿った参考経路（任意機能）

レビュー用HTMLに、要支援者と候補避難所1〜`TOP_N`の間の「道路に沿った参考経路」を追加する任意機能。
**レビューHTMLの補助情報にだけ使い、`assigned_shelters.csv` の列・値・候補順位・直線距離・ハザード判定には
影響しない**（変更前とバイト単位で同一であることを確認済み）。候補順位は引き続き直線距離による。

**有効化と既定値**

* `ENABLE_ROAD_ROUTES = True` のときだけ利用する。既定は `False` で、その場合の処理時間・成果物は従来どおり
* 有効なときだけ、道路経路のセルで osmnx の導入と `src/review/road_routes.py` の取得を行う

**道路データの取得と個人情報の扱い**

* OpenStreetMap の徒歩用道路ネットワークを OSMnx で取得する（行政区域は Nominatim、道路は Overpass API）
* 取得範囲は、糸満市の行政区域（OSM relation 4559181）と周囲約2kmの **固定範囲**。要支援者の住所・ID・座標から
  取得範囲を作らない
* 外部へ送るのは行政区域IDと取得範囲だけで、**要支援者データを外部の経路検索APIへ送信しない**
* 道路データは1回だけ取得して全員の計算で使い回し、経路計算は取得した道路グラフを使って実行環境の中で行う

**経路の求め方**

* 要支援者・避難所の地点から道路まで **150m以内** を接続対象とする（ほぼ同じ近さの道路が複数あれば、経路全体が
  最短になるものを選ぶ）
* 道路に沿った最短の経路を求め、経路の形は道路データの線の形をそのまま使う
* 次の場合は経路を算出せず、「経路を算出できません」と理由を表示する
  * 本人または避難所の地点から150m以内に道路が無い
  * 道路データ上で本人側と避難所側の道路がつながっていない
  * 地点が糸満市から1kmより外で、取得範囲の端に近い（範囲外の道路が切れていて実際より大回りになり得るため）
* **直線を道路経路として代用しない**
* 取得に失敗した場合は、レビューHTMLに作成できなかった旨を表示し、直線の表示だけを使えるようにする

**位置付け**

* 道路データ上の最短の経路の **参考** であり、通行可能性・安全性を確認した避難経路ではない
* 道路経路とハザード区域との交差判定は、現在行っていない（「本人と避難所の間のハザード区域（参考）」は
  直線についての判定である）
* 道路データの出典（© OpenStreetMap contributors / ODbL 1.0）は、背景地図（国土地理院）とは分けて画面に表示し、
  `assets/osm-roads-NOTICE.txt` を同梱する

確認の詳細（経路の正しさ、表示できない場合の扱い、処理時間・容量、確認環境）は
[docs/road-routes-check.md](./road-routes-check.md) を参照。

### 6.3 レビュー用HTML（補助成果物）

`assigned_shelters.csv` が正式なデータ成果物である。レビュー用HTML（`sheltermatch_review.zip` を展開した
`review.html`）は、**正式な割り当て結果ではなく、CSVの候補結果を職員が地図上で目視確認するための補助成果物**
である。道路経路もレビュー用の参考情報として扱う。

**オフライン利用と作り方**

* 地図ライブラリ（Leaflet。バージョン固定・SHA-256確認・LICENSE同梱）、背景地図PNG（国土地理院の地理院タイルを
  Notebook実行時に必要範囲だけ取得して画像化）、ハザード区域PNG（大分類ごと）、道路経路の座標をすべて同梱し、
  展開したフォルダだけで **外部通信なしに** 開ける。出典は地図下部に表示する
* HTMLは1ファイルで、全要支援者のデータをJSONとして埋め込み、画面には選択した1人だけを描く
* 候補の順位・距離は候補算出で得たものをそのまま使い、生成時にCSVとの一致を確認する（食い違う場合はHTMLを
  作らずに停止する）
* 背景地図の取得に失敗した場合はZIPを作らない（結果CSVは出力済みのため影響しない）

**要支援者一覧（多数件のレビュー）**

* resident_id・住所での検索
* 既存データの事実だけによる絞り込み: 「座標を確認」（`match_status` が `ok` 以外）、「ハザード該当あり」
  （既存のハザード判定のいずれかが該当。ハザード判定を実施した場合だけ）、「道路経路算出不可あり」
  （候補のいずれかで道路経路を算出できない。道路経路を作成した場合だけ）。複数の絞り込みと検索はAND条件
* 絞り込みは **安全・危険・優先度の自動評価ではない**。該当0件のときは前の要支援者の表示（地図・ハザード区域を
  含む）を残さない
* 一覧は一度に50件までを描き、前へ／次へで順に確認できる
* 内部の状態名（`match_status: ok` 等）は表示せず、座標が無い・不正な場合だけ職員向けの日本語で示す

**候補表と候補比較**

* 候補表は、順位・避難所名 → 距離 → 避難所地点のハザード → 災害種別対応（○ 対応 / △ 2階以上 / × 非対応）→
  本人と避難所の間のハザード区域（参考）の順
* 道路経路を作成した場合は、同じ距離欄で候補ごとの **直線距離** と **道路上の距離** を比較できる。道路経路を
  算出できない候補は「算出不可」とし、直線距離で代用しない。**順位は道路上の距離では変えない**
* 候補表は Tab / Shift+Tab で行を移動し、Enter・Space で候補を選べる（マウスのクリックと同じ動作）
* 候補詳細（経路情報・候補表・注記）は折りたたみ、地図を広く使える

**地図と道路経路の表示**

* 道路経路がある場合は、要支援者を選んだ時点で候補1を選択状態にし、その参考経路を表示する。候補1の経路を
  算出できない場合も、候補2・3へ自動で切り替えず、その理由を表示する。候補表から候補1〜3を切り替えられる
* 道路経路＝実線、本人と避難所を結ぶ直線＝破線、地点と道路の接続部分＝点線で区別する。道路経路の表示は
  ON/OFFできる
* 候補を選んでいるときは、選択中の候補（本人の地点・避難所・経路）へ地図を寄せる。「全候補を表示」で、本人と
  候補1〜`TOP_N`の位置関係へ戻せる
* 選択中の候補は、表（「選択中」の表示）と地図（大きいマーカー・候補名の表示）の両方で示す
* 画面上部には「避難所候補は最終的な割り当てではない」と、道路経路を作成した場合は「道路に沿った参考経路は
  通行できるか・安全かを確認した避難経路ではない」を常に表示する
* `ENABLE_HAZARD_CHECK=False` の場合もHTMLは生成でき、ハザード区域の表示・絞り込みは出さない

### 6.4 Notebook外へ切り出した実装

Notebookが「利用者が上から順に実行する手順」として読めるよう、実装の詳細は通常のPython / HTMLファイルとして
保守し、Notebook側には職員が実際に行う操作（設定・アップロード・結果と処理時間の表示）だけを残す。

| ファイル | 内容 | Notebookから呼ぶ入口 | API互換性の値 |
| --- | --- | --- | --- |
| `src/hazard/hazard_loader.py` | ハザードデータ（GeoJSON / Shapefile / 公式配布ZIP）の読込・正規化・統合 | `load_uploaded_hazards()` | `HAZARD_LOADER_API_VERSION` = 1 |
| `src/review/review_builder.py` | レビュー成果物の生成（地図素材の準備・ハザードPNG・データ組み立てとCSVとの照合・ZIP出力） | `build_review_package()` | `REVIEW_BUILDER_API_VERSION` = 2 |
| `src/review/review_template.html` | `review.html` の画面（HTML / CSS / JavaScript） | （テンプレートとして読み込む） | — |
| `src/review/road_routes.py` | OpenStreetMap道路ネットワークの取込、地点から道路への接続、道路上の最短経路の算出、レビューHTML用の経路データの生成 | `load_road_network()` / `compute_road_routes()` | `ROAD_ROUTES_API_VERSION` = 1 |

`sheltermatch.ipynb` は、Google Colab実行時にこれらのファイルをGitHub（`main`）から取得し、`importlib` で
モジュールとして読み込む（取得したコードを `exec()` で直接実行はしない）。`hazard_loader.py`・`review_builder.py`・
`review_template.html` は「外部モジュール準備」セルで、`road_routes.py` は `ENABLE_ROAD_ROUTES = True` のときだけ
道路経路のセルで取得する。各モジュールのAPI互換性の値がNotebook側の期待値と一致することを確認してから処理を
進める（互換性のない組み合わせのまま処理を続けない）。

モジュールはNotebookのグローバル変数には依存せず、必要なデータはすべて引数で受け取る。

通常のNotebook運用では、GitHubやBODIK・地理院タイル・Leaflet・OpenStreetMap等への外部通信は、Google Colabでの
処理実行時に発生する。生成済みの `sheltermatch_review.zip` は、必要な素材を同梱しているため外部通信なしで
利用できる。

## 7. 確認・テストの体制

自動テスト（CI）と実機確認は役割が異なる。CIが成功していることは、Google Colab・実データでの動作確認に
代わるものではない。

| 確認の種類 | 対象 | 使うデータ |
| --- | --- | --- |
| 自動テスト（CI） | 住所変換、道路経路の計算、レビューHTMLへのデータ受け渡し等のロジック | リポジトリ内の架空データ・架空の道路網（外部データを取得しない） |
| 開発環境での検証（`experiments/`） | Notebookのセルの通し実行、`file://` で開いたレビュー画面の自動ブラウザテスト、結果CSVの変更前との比較 | 架空の要支援者・避難所、OSM由来の道路データ（Overture Maps）等 |
| 実機確認 | Google Colabでの実行、実際のOSM道路取得・BODIK・公式ハザードデータ、実ブラウザでのレビュー画面の確認 | 実際の公開データ（要支援者は架空または実データ相当） |

### 7.1 自動テストとCI

* ローカル: `python3 -m unittest discover -s test`（必要なライブラリは `test/requirements.txt`）
* GitHub Actions（`.github/workflows/ci.yml`）: `main` 向けの Pull Request、`main` への push、`workflow_dispatch`
  で、同じテスト（`python -m unittest discover -s test`）を Python 3.12 で実行する
* CIでは依存ライブラリが import できることを確認してから、外部へ接続できない状態でテストを実行し、skip が
  1件でもあれば失敗とする。外部の行政区域・道路・ハザード・避難所データは取得しない
* 2026-09-24時点で、GitHub Actions上で38件が成功し、skip 0件であることを確認済み

詳細は [test/README.md](../test/README.md) を参照。

### 7.2 実機確認の実績

**公式ハザードデータ（Google Colab）**

以下の公式ハザードデータ5ZIP（合計106,007 Polygon）を同時に投入し、最後まで正常に処理できることを確認済み。

## 8. 今後の優先順位

本体・レビュー画面・道路に沿った参考経路・CIは、現在の目的に必要な範囲で整っている。今後は、思いつきで
機能を増やすことを優先しない。

1. **実際の職員利用・実データ相当での確認**
   * 実際のGoogle Colab新規ランタイムでの操作確認
   * 実運用規模での処理時間の確認
   * 結果CSV・レビューHTMLが、職員の判断資料として理解しやすいかの確認
2. **実利用で発生した操作上の問題・通常業務上の不具合の修正**
3. **必要性が確認できた改善だけを追加する**
   * 住居表示住所への対応は、必要になった場合だけ検討する
   * 追加の性能最適化は、実測して問題があった場合だけ行う（ハザード判定の空間インデックス化は実施済み）

**将来の改善候補（本体完成の前提条件としない）**

* 道路に沿った参考経路とハザード区域の交差判定: 「道路に沿った参考経路上で、どのハザード区域と交差するか」
  という事実情報を示すもの。安全／危険の判定や、安全経路の自動生成は行わない

## 9. 開発時のガードレール

今後の開発・レビューでは以下を守る。

### 成果物の位置付けを変えない

* `assigned_shelters.csv` が正式なデータ成果物である
* レビューHTMLは、職員の目視確認を支援する補助成果物である。道路に沿った参考経路も、レビュー用の参考情報である
* 候補順位は直線距離から変更しない。ハザード情報・道路上の距離による自動順位変更・自動除外をしない
* 「安全」「危険」「推奨」といった総合判定・独自の危険度スコアを生成しない。表示・絞り込みは既存データの事実
  だけで行う

### 本体機能と前処理・任意機能を混同しない

* 住所→座標変換や道路データ取得で問題が発生しても、距離計算・ハザード判定等の本体開発を止めない
* `ENABLE_HAZARD_CHECK`・`ENABLE_ROAD_ROUTES` のような実行時ON/OFF設定は、利用者がその処理を実行するか選択する
  ためのもので、その機能が完成対象外・不要であることを意味しない
* 実装済みの任意機能を、後から「本体外だから不要」と削らない

### 技術的に難しいことを理由に要件を勝手に縮小しない

実装・検証で問題が見つかった場合は、

1. 問題を具体的に整理する
2. 本体要件か補助機能かを確認する
3. 本体要件なら解決方法を検討する
4. 本体要件を外す必要がある場合は、利用者の判断を仰ぐ

の順とする。開発者・生成AIが独自判断で「難しいため後回し」「PoCなので不要」と要件を変更しない。

### 機能を増やしすぎない・複雑にしすぎない

* 新機能は、実利用上の必要性を確認してから追加する
* 通常業務で問題にならない極端な異常ケースへの過剰対応で、コードを複雑化しない

### 個人情報を扱う

* 実際の要支援者データ・住所データを、GitHub・テストデータ・ドキュメントへ含めない（サンプルは完全な架空データ
  とする）
* 要支援者の情報を外部の経路検索API等へ送らない

### 最終目的を維持する

このプロジェクトのゴールは、個々のライブラリやジオコーダーを動かすことではない。

**要支援者ごとに、職員が避難先を判断するために必要な候補・距離・災害情報・ハザード情報を整理して提示すること**
がゴールである。個別技術の問題に開発全体を引っ張られない。
