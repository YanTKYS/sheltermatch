## 4. 投入前に対応を検討する事項

### 4-1. 追加列・座標欄の値が、結果CSVで書き換わる

**該当箇所**: `sheltermatch.ipynb`「要支援者CSV読込・入力チェック」セル
（`read_csv_auto(residents_bytes, "要支援者一覧", dtype={"resident_id": str})`）

`resident_id` 以外の列は pandas の既定の型推定で読み込まれるため、次のことが起こる。

- 数字だけの列は数値として読まれ、先頭のゼロが消える。空欄を含む列は小数（`.0` 付き）になる
- 座標欄の `#N/A`（Excel の VLOOKUP 等の失敗で入るエラー値）・`N/A`・`NA`・`NULL` 等は、pandas の
  既定で欠損値として扱われる。そのため、値が入っているのに `no_coordinates`（空欄）と判定され、
  結果CSVでも空欄に書き換わる

**再現**（架空データ。5列に追加列3列を付けた要支援者CSV）

入力:

```text
resident_id,address,latitude,longitude,geocode_status,世帯番号,電話番号,要介護度
00001,架空住所1,26.1236,127.6658,matched,00123,0980000001,3
00002,架空住所2,#N/A,#N/A,town_not_found,00456,0980000002,
00003,架空住所3,N/A,127.67,matched,00789,,1
00004,架空住所4,26.120000,127.670000,matched,01000,0980000004,2
```

結果CSV（先頭9列）:

```text
resident_id,address,latitude,longitude,geocode_status,世帯番号,電話番号,要介護度,match_status
00001,架空住所1,26.1236,127.6658,matched,123,980000001.0,3.0,ok
00002,架空住所2,,,town_not_found,456,980000002.0,,no_coordinates
00003,架空住所3,,127.67,matched,789,,1.0,no_coordinates
00004,架空住所4,26.12,127.67,matched,1000,980000004.0,2.0,ok
```

Notebookの表示も「座標が空欄のため距離計算できなかった件数: 2件」となり、`#N/A`・`N/A` が
入っていたことは分からない。

**影響**: README の「行は削除されず、入力した値もそのまま結果CSVへ残ります」、および
[docs/bugfix-2026-09-21.md](./bugfix-2026-09-21.md) 1-2（空欄と「値は入っているが使えない」の区別）の
意図と食い違う。`resident_id` は文字列として読んでいるため影響しない。候補の算出結果も変わらない。

**対応案**: 要支援者CSVを全列文字列として読み込む（`dtype=str, keep_default_na=False`）。
座標は `read_coordinates()` で数値化しているため、候補算出はそのまま動く。修正は小さく、仕様の変更は
伴わない（`#N/A` 等は `invalid_coordinates` になり、入力値が結果CSVに残るようになる）。

### 4-2. 範囲内だが誤っている座標が `ok` として通り、警告が出ない

**該当箇所**: `sheltermatch.ipynb`「要支援者CSV読込・入力チェック」セルの `read_coordinates()`
（緯度-90〜90・経度-180〜180 だけを確認）、`src/review/review_builder.py` の `review_display_bounds()`・
`render_offline_basemap()`

緯度・経度の値の範囲だけを確認しているため、桁誤りや `0` 埋め等の座標も `match_status=ok` となり、
数千km先の避難所が候補として出力される。さらに、レビュー用HTMLの表示範囲（背景地図・ハザード画像）は
全要支援者の座標から決めているため、1件の誤った座標が全員分のレビューに影響する。

**再現**（糸満市内の架空地点に、誤った座標を1件だけ加えた場合。`review_builder.py` の
`review_display_bounds()` と背景地図のズーム選択 `_select_basemap_zoom()` を直接呼び出して確認した。
「上限を超える」は、`render_offline_basemap()` が例外を送出してレビューZIPの作成を中止する条件）

| 追加した1件 | 最寄り避難所までの直線距離 | 背景地図 |
| --- | --- | --- |
| なし（市内のみ） | — | zoom15（56枚） |
| 緯度の桁誤り（26.12 → 2.61） | 2,602 km | **zoom11（163枚）に粗くなる**（全員分） |
| `0,0`（未入力を0で埋めた） | 13,720 km | **上限を超えてレビューZIPを作成できない** |
| 経度の桁誤り（127.67 → 12.77） | 10,956 km | **上限を超えてレビューZIPを作成できない** |
| 本島北部（名護市付近）の座標 | 60 km | zoom13（144枚）に粗くなる（全員分） |

**影響**: 結果CSVでは誤った座標の行が正常な行と区別できない。レビューZIPが作れない場合も、結果CSVは
先に出力済みのため失われない。住所変換（`address_geocode.ipynb`）が付けた座標はABRの代表点のため、
主に**手入力した座標**（住居表示地域の行など）で起こる。

**対応案**: `match_status` の判定は変えずに、「最寄り避難所まで一定距離（例: 10km）を超える行」を
Notebookに一覧表示して確認を促す。レビュー用HTMLの表示範囲も、その行を除いて決める。

**判断が必要な点**: 警告の基準にする距離（例: 10km）、警告にとどめるか処理を止めるか。

### 4-3. 対象地域と重ならないハザードデータでも、全員が「区域外（False）」になる

**該当箇所**: `src/hazard/hazard_loader.py` の `load_uploaded_hazards()`、`sheltermatch.ipynb`
「候補算出とハザード判定の実行」セル

ハザード種別のファイル名判定は、年度・都道府県コードに依存しない仕様（例: `A31a-25_47_10_…` の `47`
を見ない）。そのため、別の都道府県のファイルを誤って選んでも種別は自動判定され、読込も成功する。
その結果、対象地域と重なる区域が1つも無いまま判定が行われ、全員が False になる。

**再現**: 鹿児島県付近にだけ区域がある架空のGeoJSON（ファイル名 `A31a-25_46_10_GEOJSON.geojson`）を
`ENABLE_HAZARD_CHECK = True` で読み込んだ。

```text
'A31a-25_46_10_GEOJSON.geojson'
→ ハザード種別を自動判定しました: 洪水（洪水予報河川・水位周知河川）
有効なハザードポリゴンを 1件読み込みました。
…
ハザード区域内（境界上含む）にいる要支援者数: 0件
ハザード区域内にある候補避難所の件数（延べ、TOP_N分の合計）: 0件
候補避難所への直線がハザード区域と交差する件数（延べ、TOP_N分の合計）: 0件
'assigned_shelters.csv' を出力しました。
```

結果CSVの `resident_in_hazard`・`candidate_1_shelter_in_hazard`・
`candidate_1_straight_line_intersects_hazard` はすべて `False` だった。警告は表示されない
（レビュー用HTMLの作成時に「地図の表示範囲にハザード区域が無いため…」と表示されるが、結果CSVの出力後で、
原因も分からない）。

**影響**: False は「有効な座標で判定した結果、区域外」を意味するため、実際には判定できていないのに
「区域外」と読める結果CSVになる。読込に失敗したファイルがあれば処理を止めるという、ハザード判定の
既存の方針（fail-closed）と食い違う。国土数値情報は都道府県ごとにファイルが分かれて配布されるため、
選び間違いは起こり得る。

**対応案**: ファイルごとに、要支援者・避難所の範囲と重なる区域の件数を確認し、0件のファイルがあれば
処理を止める（または警告する）。

**判断が必要な点**: 処理を止めるか、警告にとどめるか。

### 4-4. 実行するコードが、GitHub の `main` から毎回取得される

**該当箇所**: `sheltermatch.ipynb`「外部モジュール準備」セル
（`GITHUB_RAW_BASE_URL = "https://raw.githubusercontent.com/YanTKYS/sheltermatch/main/src"`）、
「道路に沿った参考経路の算出」セル

`src/` 配下のモジュールは、実行のたびに `main` の最新版を取得する。API互換性の値
（`*_API_VERSION`）の確認はあるが、これは受け渡し方の変更だけを検出するもので、処理内容の変更は検出しない。

**影響**: 運用中に `main` へ変更を取り込むと、要支援者データに対して実行されるコードが、確認のないまま
その時点で変わる。Drive に保存した古いNotebookと、新しい `src/` を組み合わせて実行することにもなる。

**対応案**: 実データで運用する版をタグ（例: `v1.0.0`）として固定し、Notebookの取得先もそのタグにする。
更新するときは、確認したうえでタグと取得先を上げる。

**判断が必要な点**: タグによる版の固定と、更新手順を運用に取り入れるか。

## 5. 軽微・運用で対応できる事項

### 5-1. レビュー画面の作成日時・道路データの取得日時がUTCで表示される

`src/review/review_builder.py` の `generated_at` と `src/review/road_routes.py` の `retrieved_at` は
`time.strftime()` で作っており、実行環境の時刻帯に従う。Google Colab の実行環境はUTCのため、
日本時間より9時間早い時刻が表示される。対応案: 日本時間（`Asia/Tokyo`）で作る（小さな修正）。

### 5-2. 住所変換をやり直すと、手入力した座標が消える

`address_geocode.ipynb`「住所CSV変換・出力」セルは、再実行のたびに全行の `latitude` / `longitude` /
`geocode_status` を変換結果で上書きする（仕様どおり）。住居表示地域（`residential_display_area`）等の座標を
手で入力した後に住所変換をやり直すと、その座標は空欄に戻る。運用で、手入力は住所変換を終えてから
最後に行うか、手入力した行を別に控えておく必要がある。

### 5-3. 建物名・部屋番号付きの住所は `parcel_not_found` になる

誤った座標にはならない（安全側）が、変換できない件数が増える。住所列から建物名・部屋番号を分けてから
変換すると改善する。

| 入力住所（架空） | 結果 |
| --- | --- |
| `沖縄県糸満市字糸満673番地2` | `matched`（地番 673-2） |
| `沖縄県糸満市字糸満673番地2 糸満ハイツ101号室` | `parcel_not_found` |
| `沖縄県糸満市字糸満673-2 コーポ糸満 101` | `parcel_not_found` |
| `沖縄県糸満市字糸満673-2-101` | `parcel_not_found`（地番 673-2-101 として照合） |
| `沖縄県糸満市字糸満673 (施設入所中)` | `parcel_not_found` |

`673-2-101` のように部屋番号をハイフンでつないだ表記は、地番の3つ目の番号として照合する。同じ地番が
実在すれば、その地番の座標になるため、部屋番号は地番と区別できる形で書くのが望ましい。

### 5-4. Colab の画面に個人情報が表示される

両Notebookは、確認のため要支援者の先頭行や、変換できなかった行の住所を画面に表示する。Notebookを
Drive にコピーして保存すると、この表示もファイルに残る。Colab の「保存時にコードセルの出力を除外する」
設定を使うか、作業後に「出力をすべて消去」してからランタイムを終了する運用が望ましい
（リポジトリ内のNotebookには実行結果が保存されていないこと、成果物のCSV・ZIPが `.gitignore` の
対象であることは確認済み）。

### 5-5. 背景地図の取得にリトライがない

`render_offline_basemap()` は地理院タイルを1枚ずつ取得し、1枚でも失敗するとレビューZIPを作らない。
結果CSVは出力済みで、セルを再実行すれば作り直せる。対応案: 一時的な失敗に備えて数回リトライする。

### 5-6. 避難所データの種類の確認

避難所一覧は、BODIKの「指定緊急避難場所」データセットを使っている。要支援者の避難先として
「指定避難所」「福祉避難所」を想定している場合は、どのデータを使うかを確認する。

## 6. 性能

**想定規模（数千人）では、性能上の問題は無い。** 処理時間は人数にほぼ比例する。いずれもサンドボックスでの
実測・見込みで、Colab での値ではない。

| 処理 | 実測・見込み |
| --- | --- |
| 候補算出（直線距離） | `geodesic` 1回 約91µs。1,000人×避難所100か所で約9秒、5,000人×150か所で約69秒 |
| ハザード判定 | 既存記録で1,000人・約10.6万ポリゴンが約6秒（[docs/bugfix-2026-09-21.md](./bugfix-2026-09-21.md)） |
| 住所変換（地番照合） | 地番10万件の想定で1件 約5.6ms。3,000件で約17秒、10,000件で約56秒 |
| 道路経路 | 既存記録で道路データの取得 約26秒（Colab）、経路計算 約3秒（1,000人） |
| review.html | 既存記録で1,000人・道路経路ありが3.6MB（開くまで約0.5秒）。5,000人なら15〜18MB程度の見込み |

直線距離の計算を `geographiclib` の直接呼び出しに変えると1回 約50µs（結果は同じ）になるが、現状でも
問題ない時間のため、変更の必要は無い。

## 7. 問題なしと確認した事項

- 既存の自動テスト38件がすべて成功する
- 住所・避難所名等の利用者データを、HTMLとして解釈されない形でレビュー画面へ埋め込んでいる
  （JSONのエスケープ、`textContent` での表示、地図のツールチップもDOM要素で渡している）
- ZIP展開時のパストラバーサル対策（全エントリを検査してから展開する）
- ハザードデータの一部が読み込めない場合に処理を止める（fail-closed）
- レビューHTMLの内容と結果CSVが一致しない場合に、HTMLを作らずに止める
- 要支援者の座標が避難所と完全に一致する場合（距離0m）も、ハザード判定・道路経路が正しく動く
- 成果物（`assigned_shelters.csv`・`*_geocoded.csv`・`sheltermatch_review.zip` 等）が `.gitignore` の対象
- リポジトリ内の両Notebookに実行結果（出力）が保存されていない

## 9. 次の対応（案）

| 事項 | 修正の規模 | 判断が必要な点 |
| --- | --- | --- |
| 4-1 追加列・座標欄の値の書き換え | 小（読込の指定を変更） | なし（仕様どおりの動作に直す） |
| 4-2 誤った座標の警告 | 小〜中 | 警告の基準距離、警告か停止か |
| 4-3 対象地域と重ならないハザードデータ | 小〜中 | 停止か警告か |
| 4-4 実行コードの版の固定 | 小（取得先の変更）＋運用 | タグ運用を取り入れるか |
| 5-1 日時のUTC表示 | 小 | なし |
| 5-2〜5-6 | 運用で対応（5-5のみ小さな修正） | 運用手順への反映 |

4-1 と 5-1 は結果の内容を変えない小さな修正のため、判断を待たずに対応できる。4-2〜4-4 は、
上の判断をいただいてから対応する。
