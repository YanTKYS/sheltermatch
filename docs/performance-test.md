# sheltermatch.ipynb 性能・出力内容の確認結果

`sheltermatch.ipynb` が実運用規模（100 / 500 / 1000人程度）でどの程度の時間で動くか、また出力CSVが
職員が確認する上で問題ない内容かを確認した記録。**性能改善は行わず、まず実測結果を残すことを目的と
している。**

## 0. 実測環境について（重要な注記）

今回の実測は、このタスクを行ったサンドボックス環境（Google Colabではないローカル実行環境）で行った。
理由は、このサンドボックスから外部ネットワークへ接続できず、Google Colabの起動、BODIK Data API
（`data.bodik.jp`）への実アクセス、ABR公式サイト・国土数値情報・沖縄県公式サイトからの実データ
ダウンロードのいずれも行えないため。

そのため、以下は**実測**であるが、**本番の実行条件（Google Colab、実際のBODIK API、実際の公式
ハザードZIP本体）そのものではない**ことに注意すること。

- **避難所データ**: 実際のBODIK APIへは接続できないため、55件の架空避難所データ（日本語ODS列名
  `名称`/`緯度`/`経度`、`災害種別_洪水`等の列を含む）で `fetch_shelters_from_bodik()` の呼び出し先
  (`requests.get`) をモック化し、`sheltermatch.ipynb` のBODIK取得・列名変換・災害種別解析コードは
  そのまま実行した。
- **ハザードデータ**: 実際の公式ZIP（`A31a-25_47_10_GEOJSON.zip` 等5点）はダウンロードできないため、
  **同じファイル名**（`detect_hazard_type()` によるファイル名自動判定が実際に効くことを確認するため）
  かつ**docsに記載の合計約106,000件と同規模のPolygon数**を持つ、**幾何形状が完全に架空**のZIPを
  代用データとして生成し、`sheltermatch.ipynb` のZIP展開・GeoJSON読込・CRS処理・
  `derive_feature_hazard_types()`（A33の現象種類・区域区分、津波の「分類」属性の反映）を含む
  ハザード読込コードをそのまま実行した。ポリゴンの位置・形状・件数配分は検証用の架空データであり、
  実際の浸水想定区域・警戒区域を表すものではない。
- **`sheltermatch.ipynb` 本体のロジックはテスト用に一切書き換えていない**。今回のPRで追加した
  `time.perf_counter()` による計測コードのみが本体への変更であり、実行したのはその計測込みの
  実セルコード（ノートブックのセルソースをそのまま抽出して実行）である。
- 実際のGoogle Colab実行時間、実際のBODIK API・公式ハザードZIP本体による実測は**未実施**。
  これらは今回の環境では測定できないため、未測定として明記する（推測値は記載しない）。

## 5. 処理時間（実測・ENABLE_HAZARD_CHECK=True）

### 計測方法（TIMINGSのリセットについて）

`TIMINGS` は「要支援者CSV読込・入力チェック」セルの冒頭でその都度リセットされる。そのため、
「合計」は**そのセルを実行した時点から結果CSV出力までに実際に実行された工程だけ**を積み上げた
値になり、それより前に別のタイミングで読み込んだハザード・避難所データの時間が混入することはない
（ハザードGeoDataFrame・避難所DataFrame自体は再利用できるが、計測用の辞書はリセットされる）。

今回は、この挙動に合わせて2通りの操作を再現して計測した。

- **100件**: 「ランタイム → すべてのセルを実行」に相当する、要支援者CSV読込→避難所データ取得→
  ハザードデータ読込→候補算出→結果CSV出力までの通し実行（全工程がTIMINGSに記録される）。
- **500件・1000件**: 避難所データ・ハザードデータは100件実行時に読み込んだものをそのまま再利用し、
  「要支援者CSV読込・入力チェック」セルだけをリランして候補算出・結果CSV出力へ進む運用
  （避難所データ取得・ハザードデータ読込の工程はTIMINGSに記録されず、合計にも含まれない）。

| 処理 | 100件（通し実行） | 500件（要支援者CSVのみリラン） | 1000件（要支援者CSVのみリラン） |
| --- | --- | --- | --- |
| 要支援者CSV読込・入力チェック | 0.00秒 | 0.00秒 | 0.01秒 |
| 避難所データ取得・整形 | 0.00秒 | （リランせず再利用・未計測） | （リランせず再利用・未計測） |
| ハザードデータ読込・統合 | 1.86秒 | （リランせず再利用・未計測） | （リランせず再利用・未計測） |
| 候補算出＋ハザード判定 | 6.92秒 | 36.14秒 | 72.73秒 |
| 結果CSV生成 | 0.01秒 | 0.03秒 | 0.06秒 |
| **合計（今回実行した工程のみ）** | **8.79秒** | **36.18秒** | **72.79秒** |

100件の合計には避難所データ取得・ハザードデータ読込の時間が含まれるが、500件・1000件は
避難所データ・ハザードデータを再利用しているため、その時間を含まない「候補算出＋ハザード判定＋
CSV入出力」だけの合計になっている（Notebookが表示する合計と一致する）。

## 6. スケーラビリティの確認

候補算出＋ハザード判定の時間は、要支援者数にほぼ比例して増加した。

- 100→500件（5倍）: 6.92秒 → 36.14秒（約5.2倍）
- 500→1000件（2倍）: 36.14秒 → 72.73秒（約2.0倍）

今回の規模・代替データでは、急激な非線形の悪化（O(N²)的な跳ね上がり等）は見られなかった
（実測値は実行のたびに数秒程度前後する。入力データ自体は固定シードで同一だが、計測している
壁時計時間はマシン負荷等の影響を受けるため）。

## 7. ボトルネック

**候補算出＋ハザード判定**が全体時間の95%以上を占め、明確なボトルネックだった。内訳を見ると、
避難所55件との直線距離計算（`geopy.distance.geodesic`、要支援者数×55回）自体は軽く、時間の大半は
ハザード判定（要支援者本人1回＋候補avg3件×2種類＝要支援者1人あたり最大7回の
`GeoSeries.intersects()` 呼び出しを、106,000件のポリゴン全体に対して都度行う）が占めていると
考えられる。空間インデックス（`STRtree`等）を使わない現在の実装では、この呼び出し1回ごとに
ポリゴン全件を走査するため、要支援者数に比例して時間が増える。

**次に検討すべき最小の改善（今回は実施しない）**: ハザード判定用GeoDataFrameに対する空間インデックス
の活用（例: `geopandas.sjoin` や `shapely.STRtree` によるインデックス化）。ただし、これは次回以降、
性能上の必要性が明確になった場合にのみ検討する（本タスクでは実施しない）。

> **追記（2026-09-21）**: 上記の空間インデックス活用は、その後のバグ修正・リファクタリングで実施済み。
> 本ドキュメントの「5. 処理時間」の数値は**その修正前**の実測値である。修正後の実測値と、
> 判定結果が変わっていないことの確認結果は [docs/bugfix-2026-09-21.md](./bugfix-2026-09-21.md) を参照。

## 9. 出力CSVの職員目線での確認

Excel等で1人分を横方向に確認する前提で、現在の出力列順を確認した。

### 現状（確認前）

```
resident_id, address, latitude, longitude, geocode_status,
resident_in_hazard, resident_hazard_types,
candidate_1, distance_1_m, candidate_1_disaster_support,
candidate_1_shelter_in_hazard, candidate_1_shelter_hazard_types,
candidate_1_straight_line_intersects_hazard, candidate_1_straight_line_hazard_types,
candidate_2, ..., candidate_3, ...,
match_status   ← 一番最後
```

### 問題

`match_status`（座標→候補算出そのものが成功したか）が、候補・ハザード関連のすべての列より後、
出力の一番最後に追加されていた。職員が左から右へ1行を確認する場合、候補や距離を先に目にしてから
初めて「実はこの行は座標が無効で候補が出ていない」と分かる順序になっており、確認の順序として
分かりにくい。

### 修正案・対応

`match_status` を、共通住民CSVの5列（`resident_id,address,latitude,longitude,geocode_status`）の
直後・候補列より前に並べ替えた（値の計算方法は変更せず、列の並び順のみの変更）。これは軽微かつ
明確な改善のため、本PRで対応済み。

```
resident_id, address, latitude, longitude, geocode_status, match_status,
resident_in_hazard, resident_hazard_types,
candidate_1, distance_1_m, candidate_1_disaster_support,
candidate_1_shelter_in_hazard, candidate_1_shelter_hazard_types,
candidate_1_straight_line_intersects_hazard, candidate_1_straight_line_hazard_types,
candidate_2, ..., candidate_3, ...
```

候補1→距離1→災害対応1→ハザード情報1→候補2→候補3、という並びはこの並べ替え前から維持されている
（候補ごとにまとまっており、変更していない）。

### その他の観察（今回は対応しない）

- `候補N_straight_line_hazard_types` 等の値（例:
  `土砂災害:土石流:土砂災害特別警戒区域(指定前)`）は情報量が多く長い。Excelで複数候補を横に並べて
  比較する際に列幅を広く取る必要がある可能性がある。ただし、値の意味・粒度を変えることは出力仕様の
  変更にあたるため、今回は現状維持とし、必要であれば別途検討する。
- 上記以外に、候補1〜3の比較しやすさ・情報の埋もれについて、今回のデータ量（55避難所・TOP_N=3）では
  致命的な問題は見られなかった。

## 10. 実行時に問題があったか

今回の代替環境・代替データでの実行では、エラー・例外・データ欠損等の問題は発生しなかった。
`sheltermatch.ipynb` 本体のロジックは変更していない（`time.perf_counter()` による計測コード、
`match_status` 列の並べ替え、および計測用`TIMINGS`辞書を要支援者CSV読込セルの冒頭でリセットする
処理のみを追加した）。

レビューで、避難所・ハザードデータを再利用しつつ要支援者CSVだけをリランした場合に、前回実行分の
`TIMINGS["hazard"]`/`TIMINGS["shelters"]`が残り、合計へ混入する不具合を指摘され修正した
（5.の「計測方法」を参照）。
