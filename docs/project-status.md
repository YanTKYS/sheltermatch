# sheltermatch 現状整理・開発方針

更新日: 2026-09-22

## 1. この文書の目的

`sheltermatch` の現在地と、本体として完成させる範囲を明確にする。

個別機能で技術的な問題が発生した場合でも、その問題だけを理由として本来の目的や優先順位を変更しないための開発上のガードレールとして扱う。

特に、補助機能で問題が発生したことを理由に、本体機能まで「難しいので後回し」「PoCなので不要」などと再解釈しない。

---

## 2. sheltermatch の目的

要支援者ごとに、避難所候補を機械的に最終決定するものではない。

以下の情報を整理し、職員が避難先を判断するための一次資料を作成することを目的とする。

1. 要支援者の位置
2. 避難所の位置
3. 距離が近い避難所候補
4. 避難所の災害種別対応情報
5. 要支援者・候補避難所・両者を結ぶ直線とハザード区域との位置関係

最終的な避難所の決定は職員が行う。

---

## 3. 完成範囲の整理

sheltermatch本体の主要機能は、現時点で概ね完成しているものとして扱う。

本体の目的は、**要支援者ごとに、職員が避難先を判断するために必要な候補・距離・避難所の災害対応情報・ハザード情報を整理して提示すること** である。

以下は、この完成範囲に含めない（完成条件として新たに要求しない）。

* 住所→座標変換
* 道路ネットワークによる経路探索
* 安全経路の自動判定
* ハザードによる候補の自動除外
* 独自の危険度スコア
* KML対応

これらが将来的に不要という意味ではなく、本体の完成をこれらの実現に依存させないという整理である。

## 4. 本体として完成させる機能

### 4.1 要支援者データの読込

要支援者一覧CSVを読み込み、住所・緯度・経度等を保持する。

座標が欠損している行や不正な行も削除せず、処理結果に残す。

座標が利用できない場合は、候補計算を行わず `match_status` 等で状態を明示する。

### 4.2 避難所データの取得

避難所一覧は、原則としてBODIK Data APIから糸満市の自治体標準オープンデータセットを取得する。

API取得に失敗した場合はCSVアップロードへフォールバックできる。

自治体標準ODSの以下の情報を利用する。

* 名称
* 緯度
* 経度
* 災害種別

災害種別については、

* `1` = 対応済み
* `2` = 2階以上であれば対応済み
* 空欄 = 未対応

を区別して保持する。

この情報は避難所そのものの指定状況であり、GeoJSON/Shapefileによるハザード区域判定とは別の情報として扱う。

### 4.3 避難所候補の算出

要支援者と各避難所の座標から `geopy.distance.geodesic` により直線距離を計算する。

既定では距離が近い上位3件を候補として出力する。

これは道路距離・避難経路ではない。

距離順位は、以下の情報によって自動変更しない。

* 避難所の災害種別対応
* ハザード区域判定
* その他の独自スコア

これらは職員判断のための別情報として出力する。

### 4.4 ハザード区域判定

ハザード区域判定は **sheltermatch本体の完成対象** である。

実行時には `ENABLE_HAZARD_CHECK` によって使用するか選択できるが、これは利用時の任意設定であり、開発上の優先度が低いことを意味しない。

読み込んだGeoJSON / ShapefileをEPSG:4326のPolygon / MultiPolygonとして統合し、少なくとも以下を判定する。

有効なPolygon / MultiPolygonは一切変更せずそのまま使う。公式配布データに実際に含まれている
`is_valid=False` のPolygon / MultiPolygon（自己交差等）は、`shapely.make_valid()` で直してから使う
（直した結果がGeometryCollectionになる場合はPolygon / MultiPolygon成分だけを使い、区域として
使える形にならなかったものは区域判定対象外とする）。空・欠損のジオメトリ、Polygon / MultiPolygon
以外のジオメトリは、従来どおり区域判定対象外とする。直した行も元の `hazard_type` をそのまま
引き継ぎ、種別・カテゴリを再解釈しない。

#### 要支援者地点

要支援者地点がハザード区域の内部または境界上にあるか。

#### 候補避難所地点

各候補避難所地点がハザード区域の内部または境界上にあるか。

#### 要支援者と候補避難所を結ぶ直線

要支援者と候補避難所を単純な `LineString` で結び、その直線がハザード区域と交差するか。

これは **道路上の避難経路の安全性判定ではない**。

道路ネットワーク、通行可能性、高低差、リアルタイム道路状況等は計算していないため、「安全な避難経路」と表現しない。

対応対象としているハザード種別と、その詳細区分の保持状況は以下のとおり。

* 洪水（国土数値情報A31a）: ZIP内部のサブフォルダをカテゴリとして保持する（実データで確認済みのカテゴリは
  `10_計画規模` / `20_想定最大規模` / `30_浸水継続時間` / `41_家屋倒壊等氾濫想定区域_氾濫流` /
  `42_家屋倒壊等氾濫想定区域_河岸侵食`）
* 土砂災害（国土数値情報A33）: ファイル名から入力なしで自動判定し、公式属性 `A33_001`（現象の種類）/
  `A33_002`（区域区分）から `急傾斜地の崩壊` / `土石流` / `地滑り` と、`土砂災害警戒区域(指定済)` /
  `土砂災害特別警戒区域(指定済)` 等の詳細区分をそのまま保持する
* 津波（沖縄県LEVEL1〜7）: 実データの `分類` 属性（例: `0.01m以上0.3m未満`）を保持する
* 高潮（沖縄県）: ファイル名からカテゴリ（`最大浸水深` / `浸水継続時間`）を保持する

複数種類に該当する場合は、該当種別をすべて保持する。

ハザード判定結果による候補の自動除外・自動順位変更は行わない。

詳細なデータ取得・利用手順は [docs/hazard-data.md](./hazard-data.md) を参照。

## 5. 住所→座標変換の位置付け

住所→座標変換は **sheltermatch本体処理の前処理** とする。

sheltermatch本体の完成を、この機能の完成に依存させない。

緯度・経度があらかじめ用意された要支援者データで、

* 避難所候補算出
* 災害種別情報
* ハザード判定
* 結果CSV出力

まで完走できる状態を先に完成させている（詳細は下記「7. 実機確認の実績」を参照）。

### これまでの検証

当初はJageocoderを検討した。

しかし、

* Google ColabのPython 3.13と `jageocoder-converter` の互換性問題
* Jageocoder 2.2系でのconverter API非互換
* converterが参照する住所データ取得先での403

等が発生した。

その後、デジタル庁公式 `@digital-go-jp/abr-geocoder` 2.3.1へ切り替えた。

ABR Geocoder自体は地域限定データ生成に対応しているが、GitHub-hosted runnerからアドレス・ベース・レジストリの配布データへアクセスするとCloudFrontから403が返る問題が確認された。

これはABR Geocoder公式リポジトリでも既知の外部要因として報告されている。

さらにその後、同じくデジタル庁公式のABR Geocoder（`abrdb`/`abrg` + PostgreSQL + DuckDB構成、`experiments/abr_geocoder_poc.ipynb`）を改めて検証した。ネイティブビルド・PostgreSQL準備・沖縄県限定`abrdb init`までは成功したが、Colab等のクラウド環境からABR公式データ本体を取得する段階で、同様にアクセスエラー（403）となる問題が確認された。

### 現在の方式: ABR公式CSVの手動取得・直接照合

JageocoderもABR Geocoderも、辞書・キャッシュ生成のために配布データを自動ダウンロードする構成だったため、代わりに、利用者がABR公式CSVを手動で取得し、pandasで直接照合するだけの方式（`experiments/abr_csv_geocode_poc.ipynb` で検証）を確認した。

その結果、糸満市の地番住所については、この方式で実用的に座標を取得できることを確認した。この検証済みロジックをそのまま再利用し、実運用で繰り返し使える独立Notebook `address_geocode.ipynb` を用意している。

* `address_geocode.ipynb` は sheltermatch本体へは統合しない、独立した前処理用Notebookである
* 公式ABR CSV3種類（町字マスタ・地番マスタ・地番位置参照）を利用者が手動アップロードし、対象自治体のデータを抽出・結合して使用する（自動ダウンロードは行わない）
* 出力CSVには `latitude`/`longitude` が含まれ、sheltermatchの要支援者CSVとしてそのまま利用できる
* ABRマスター準備と住所CSV変換を分離しており、同じColabランタイムが生きている間は、住所CSVを差し替えるたびにABR ZIPを再アップロードする必要はない
* 住居表示住所（`rsdt_addr_flg=1`の町字）は、現在の3データだけでは正しく座標化できるとは限らないため、`residential_display_area`として地番確定を明示的に保留し、無理に座標化しない

実機確認では、`experiments/address_conversion_test_input.csv`（8件）で6件matched・1件town_not_found・1件blank_addressとなり、通常表記・都道府県省略・全角数字・「番地」表記省略のいずれも同じ地番・座標へ一致することを確認済み。

住所表記の揺れ（全角／半角、漢数字の丁目、ハイフン類、空白、「字」「大字」の有無、`番地`/`番`/`号`/`の`
の表記差）への対応は、`test/test_address_conversion.py` で回帰テストしている
（`python3 -m unittest discover -s test`）。別の住所を同一視していないことも同じテストで確認する。

データ取得元・利用手順・`geocode_status`の詳細は [docs/address-data.md](./address-data.md) を参照。

### 今後

住居表示住所への対応や、他自治体への展開が必要になった場合に、追加データ・追加検証を検討する。地番住所についてはABR公式CSV直接照合方式が成立しているため、特定方式をこれ以上追いかけることを本体完成の前提条件とはしない。

## 6. 現時点で実装済みの主要機能

現行Notebookには、以下が実装されている。

* 要支援者CSV読込
* 座標の欠損・範囲外チェック
* BODIK Data APIからの避難所取得
* API失敗時のCSVフォールバック
* 自治体標準ODS列名の正規化
* 避難所の災害種別対応情報の保持
* geodesicによる距離計算
* 上位 `TOP_N` 候補算出
* GeoJSON単体・GeoJSONを含むZIP・Shapefileを含むZIPの読込(展開・変換不要でアップロード可能。
  ZIP内の拡張子は `.SHP` / `.GEOJSON` のような大文字でも読み込める)
* ZIP内パストラバーサル対策・CP932ファイル名文字化けの復元
* CRSのWGS84統一(CRSが無いShapefileは座標値から経緯度データかどうかを判定)
* Polygon / MultiPolygon検証(それ以外のgeometry typeは区域判定対象外として除外し、件数を集約表示)
* 公式データに含まれる不正なPolygon / MultiPolygon(自己交差等)の `shapely.make_valid()` による修復
  (有効なジオメトリは変更しない。GeometryCollectionはPolygon成分のみ採用。修復・除外の件数を集約表示)
* 洪水(国土数値情報A31a)のファイル名自動判定とZIP内カテゴリ(計画規模/想定最大規模等)の保持
* 土砂災害(国土数値情報A33)のファイル名自動判定と `A33_001`/`A33_002` による詳細分類の保持
* 津波(沖縄県LEVEL1〜7)の `分類` 属性保持
* 高潮(沖縄県)のファイル名からのカテゴリ保持
* 要支援者地点のハザード判定
* 候補避難所地点のハザード判定
* 要支援者-候補避難所間の直線交差判定
* 複数ハザード種別の保持
* UTF-8 BOM付き結果CSV出力
* レビュー用HTML出力(`sheltermatch_review.zip`。下記「6.1」を参照)
* 座標欠損・不正行を削除せず結果へ保持(入力した値も書き換えずそのまま保持)
* 座標欄が空欄(`no_coordinates`)と、値は入っているが使えない(`invalid_coordinates`)の区別
* ハザードデータ未読込のまま候補算出セルを実行した場合の停止(全行を「区域外」と出力しない)
* 前回の結果CSVをそのまま再投入した場合の結果列の置き換え

ハザードデータの取得元・具体的な操作手順は [docs/hazard-data.md](./hazard-data.md) を参照。
ハザード読込処理の置き場所は下記「6.2」を参照。

### 6.1 レビュー用HTML(補助成果物)

`assigned_shelters.csv` が正式なデータ成果物である。レビュー用HTMLは、**正式な割り当て結果ではなく、
CSVの候補結果を職員が地図上で目視確認するための補助成果物** である。

最終出力セルで `sheltermatch_review.zip` を出力する。展開して `review.html` を開くと、要支援者を
1人ずつ選んで、要支援者地点・候補避難所1〜3・両者を結ぶ直線・ハザード区域を地図で確認できる。

実装の置き場所は「6.2 Notebook外へ切り出した実装」を参照。

**地図ライブラリ(Leaflet)・背景地図PNG・ハザードPNGはいずれも成果物へ同梱するため、展開した
フォルダだけで、外部通信なしに `review.html` を開ける(背景地図も既定でON)。** 背景地図は
国土地理院の地理院タイル(淡色地図)を、Notebook実行時(インターネット接続あり)にだけ必要な
範囲だけ取得してPNGへモザイク・切り出ししたもので、タイル一式はそのままでは同梱しない。
糸満市周辺の詳細背景(`assets/basemap_itoman.png`。ハザードPNGと同じ表示範囲・同じ投影で
生成するため位置がずれない)と、沖縄本島全体の概要背景(`assets/basemap_okinawa_mainland.png`。
固定範囲)の2種類を作る。取得前に必要タイル数・想定出力サイズ・使用ズームを表示し、タイル数が
上限を超える場合は黙って大量取得せず処理を中止する(安全策)。地理院タイルの出典
(`国土地理院`)は `review.html` の地図下部に表示する。背景地図の生成に失敗した場合は
`sheltermatch_review.zip` 自体を作らない(結果CSVは既に出力済みのため影響しない)。

* HTMLは1ファイルのみ。全要支援者のデータをHTML内へJSONとして埋め込む(要支援者ごとのHTMLや
  外部`data.json`は作らない)。画面には選択した1人だけを描画する
* 外部CDNを参照しない。Leaflet本体(JS/CSS/画像)はバージョンを固定して`assets/`へ同梱し、
  取得した内容をSHA-256で確認してから書き込む。Leaflet(BSD 2-Clause License)の再配布条件に
  従い、公式LICENSE本文もそのまま`assets/leaflet-LICENSE.txt`として同梱する
* 表示するハザードは、本体で処理済みの `hazard_gdf` から大分類(津波/洪水/高潮/土砂災害/その他)
  ごとの透過PNGへ描き出す。約18万件のポリゴンをブラウザへ渡さない。表示用画像のために別の
  ハザード判定・修復ロジックは持たない
* 背景地図PNG・ハザードPNGはいずれもWeb地図と位置がずれないよう、表示範囲をEPSG:3857へ
  変換した矩形の中で作る。表示順は「背景地図 → ハザードPNG → 直線 → 要支援者・候補避難所」を
  Leafletの専用pane(zIndex固定)で保証する
* サイドバーに沖縄本島の概要図(小さな画像)を表示し、詳細図(メイン地図)の表示範囲を矩形、
  選択中の要支援者位置を点でHTML/CSSにより重ねる。要支援者を切り替えると、メイン地図・
  候補1〜3・直線・ハザード表示と同期して更新される
* サイドバーの要支援者一覧は、件数が多くても検索が重くならないよう一度に50件までを描く。
  描く範囲は選択中の要支援者を含むページとし、「次へ」で51人目以降へ進んだ場合も一覧に
  選択中の行が残る(1000件の架空データで確認済み)
* 候補の順位・距離は候補算出ループで得たものをそのまま使い、HTML用に計算し直さない。
  生成時にCSVとの一致(件数・resident_id・候補名・距離・ハザード判定)を確認し、
  食い違う場合はHTMLを作らずに処理を停止する
* 候補避難所の緯度・経度はCSVへは追加せず、HTML表示用の内部データとしてのみ保持する
* 画面では「割り当て済み」とは表示せず、避難所候補・候補1/2/3として扱う。要支援者と避難所を
  結ぶ線は直線(直線交差判定に使っている線)として表示し、避難経路とは表示しない
* `ENABLE_HAZARD_CHECK=False` の場合もHTMLは生成でき、背景地図・概要図は表示されるが、
  ハザードPNG・レイヤ操作は表示しない

### 6.2 Notebook外へ切り出した実装

Notebookが「利用者が上から順に実行する手順」として読めるよう、実装の詳細は通常のPython /
HTMLファイルとして保守し、Notebook側には職員が実際に行う操作だけを残す。

| ファイル | 内容 | Notebookから呼ぶ入口 |
| --- | --- | --- |
| `src/hazard/hazard_loader.py` | ハザードデータ(GeoJSON / Shapefile / 公式配布ZIP)の読込・正規化・統合 | `load_uploaded_hazards()` |
| `src/review/review_builder.py` | レビュー成果物の生成(地図素材の準備・ハザードPNG・データ組み立て・ZIP出力) | `build_review_package()` |
| `src/review/review_template.html` | `review.html` の画面(HTML / CSS / JavaScript) | (テンプレートとして読み込む) |

`sheltermatch.ipynb` は「外部モジュール準備」セルで、Google Colab実行時にこの3ファイルを
GitHub(`main`)から取得して一時ディレクトリへ保存し、`importlib` でモジュールとして読み込む
(取得したコードを `exec()` で直接実行はしない)。取得に失敗した場合は分かりやすいエラーで停止する。

各モジュールは `HAZARD_LOADER_API_VERSION` / `REVIEW_BUILDER_API_VERSION` を持ち、Notebook側が
期待値と一致することを確認してから処理を進める(互換性のない組み合わせのまま処理を続けない)。

Notebook側に残すのは、`ENABLE_HAZARD_CHECK` 等の設定・ファイルのアップロード操作・必要なときの
ハザード種別入力・処理結果と処理時間の表示・後続の候補算出/ハザード判定である。モジュールは
Notebookのグローバル変数には依存せず、必要なデータはすべて引数で受け取る。

GitHubへ通信するのは、**Google Colabで処理を実行するときだけ** である。できあがった
`sheltermatch_review.zip` は従来どおり、外部通信なしで利用できる(必要なものはすべて同梱する)。

## 9. 開発時のガードレール

今後の開発・レビューでは以下を守る。

### 本体機能と前処理を混同しない

住所→座標変換で問題が発生しても、距離計算・ハザード判定等の本体開発を止めない。

### 技術的に難しいことを理由に要件を勝手に縮小しない

実装・検証で問題が見つかった場合は、

1. 問題を具体的に整理する
2. 本体要件か補助機能かを確認する
3. 本体要件なら解決方法を検討する
4. 本体要件を外す必要がある場合は、利用者の判断を仰ぐ

の順とする。

開発者・生成AIが独自判断で「難しいため後回し」「PoCなので不要」と要件を変更しない。

### `任意機能` と `開発対象外` を混同しない

`ENABLE_HAZARD_CHECK` のような実行時ON/OFF設定は、利用者がその処理を実行するか選択するためのもの。

その機能がsheltermatchの完成対象外であることを意味しない。

### 最終目的を維持する

このプロジェクトのゴールは、個々のライブラリやジオコーダーを動かすことではない。

**要支援者ごとに、職員が避難先を判断するために必要な候補・距離・災害情報・ハザード情報を整理して提示すること** がゴールである。

個別技術の問題に開発全体を引っ張られない。
