# v1.0.0 で実装・検証した拡張機能の記録

更新日: 2026-10-01

v1.0.0 で実装・確認したが、担当部署の業務要件の確認を受けて **v1.1.0 の通常運用から外した機能** の記録。
機能の不具合・失敗による削除ではない。実装は `v1.0.0` タグに残っており、今後、別の業務要件で必要になった
場合に参照・再利用できる。

> 実装を確認する場合は、`v1.0.0` タグ（`git show v1.0.0:<パス>` または GitHub 上でタグを選んで表示）を参照すること。
> 現行の `main` から該当コードは削除している。`v1.0.0` タグは付け直さない・削除しない。

## 1. 背景

担当部署による実運用レビューで、次の業務要件が確認できた。

1. 必要なのは、避難所までの **直線距離**
2. 実際にどの経路を使うかは、本人への聞き取り等によって職員が判断する
3. ハザードについて確認したいのは、避難所や経路ではなく **本人住所がハザード区域内にあるか**
4. 集計情報として、各ハザード区域内に何人の住所があるかを確認したい
5. 結果CSVは情報が多すぎる
6. 避難所がどの災害種別に対応しているかは、今回の成果物には不要

これを受けて v1.1.0 は「**要支援者本人の住所についてハザードの影響を確認し、直線距離が近い避難所候補を職員へ
提示する**」ことに絞った。以下の機能は、いずれも v1.0.0 で技術的に動作することを確認していたが、この業務
要件には不要なため、通常運用から外している。

| 外した機能 | v1.1.0 での扱い |
| --- | --- |
| OpenStreetMap / OSMnx による道路経路探索 | 現行コード・Notebook・テスト・`experiments/` から削除 |
| 道路上距離 | 同上（レビュー画面にも出さない） |
| 候補避難所地点のハザード判定 | 判定せず、CSV列・レビュー表示とも削除 |
| 本人→候補直線のハザード交差判定 | 同上 |
| 避難所の災害種別対応情報 | 変換・保持・出力をやめ、BODIKの元データの `災害種別_` 列は読み捨てる |

## 2. OpenStreetMap / OSMnx による道路経路探索（道路に沿った参考経路）

### 実装していたこと

* `ENABLE_ROAD_ROUTES = True` のときだけ、レビュー用HTMLに「道路に沿った参考経路」を追加する任意機能
  （既定は `False`。結果CSVには影響しない）
* OpenStreetMap の徒歩用道路ネットワークを OSMnx で1回だけ取得（行政区域は Nominatim、道路は Overpass API。
  糸満市の行政区域＋周囲約2kmの固定範囲）し、全員の計算で使い回す。要支援者の座標・住所・IDは外部へ送らず、
  経路計算はColab内で行う
* 要支援者・避難所の地点を、150m以内の道路へ接続（ほぼ同じ近さの道路が複数あれば、経路全体が最短になるもの）し、
  道路上の最短経路を求めて、道路データの線の形のまま表示
* 道路が近くにない・道路がつながっていない・取得範囲の端に近い場合は、直線で代用せず「経路を算出できません」と表示
* レビュー画面での候補1の自動選択、候補表での切り替え、道路経路（実線）・直線（破線）・接続部分（点線）の描き分け、
  経路表示のON/OFF、「道路経路算出不可あり」の絞り込み、OSM出典・`osm-roads-NOTICE.txt` の同梱
* 実装: `src/review/road_routes.py`、`src/review/review_builder.py` / `review_template.html` の経路表示部分、
  `test/test_road_routes.py`、`experiments/road_routes/`（確認用スクリプト）

### 技術的に動作確認できていたこと

* Google Colab で、OSMnx による Nominatim・Overpass API からの道路データ取得（約26.4秒）、経路の算出
  （`road_routes.status = "ok"`）、経路情報を含む `sheltermatch_review.zip` の生成に成功
* 2026-09-29 の実際の運用データで、座標のある1,024人・候補3,072件の経路をすべて作成できた
* 開発環境（Overture Maps の道路データ・自動ブラウザテスト）で、経路が道路の形に沿うこと、networkx と同じ最短距離に
  なること、遠すぎる道路へ接続しないこと、結果CSVが変わらないこと、候補1の自動選択・切り替え等を確認
* 確認の詳細は [docs/road-routes-check.md](../road-routes-check.md)

### なぜ v1.1.0 で外したか

実装・実機確認まで行ったが、担当部署では **実際の避難経路を本人への聞き取り等によって職員が判断する** ため、
システムが道路経路や道路上の距離を示す必要はなく、通常業務には不要と判断した。あわせて、OSMnx の導入・道路データの
取得（外部通信・数分の処理時間）が不要になり、Notebookとレビュー成果物が簡素になる。

### 将来の再利用の可能性

* 職員が聞き取りで決めた経路の確認や、徒歩での所要時間の目安が業務上必要になった場合
* 要支援者以外（地域全体）を対象にした、避難所までの徒歩圏の分析を行う場合
* 再利用する場合は、`v1.0.0` の `road_routes.py` と `docs/road-routes-check.md` を出発点にし、OSMのライセンス
  （ODbL 1.0）の表示、道路が取得範囲の端に近い場合の扱い、直線で代用しない方針を引き継ぐ

## 3. 道路上距離

### 実装していたこと

道路経路探索の結果として、道路への接続点の間の距離（道路上の距離）と、地点と道路の接続部分の長さを、レビュー画面の
距離欄に「直線」と並べて表示していた。道路上の距離が無い候補は「算出不可」と表示し、直線距離で代用しなかった。
候補の順位は直線距離のままで、道路上の距離では変えていなかった。

### 技術的に動作確認できていたこと

上記「道路経路探索」の確認と同じ（道路上の距離が最短経路の長さと一致することを、開発環境で確認）。

### なぜ v1.1.0 で外したか

道路経路探索と同じ理由。担当部署が必要とするのは本人住所から避難所までの **直線距離** で、道路上の距離は
業務判断に使わない。

### 将来の再利用の可能性

道路経路探索と同じ。直線距離と道路上の距離の乖離が大きい候補を職員へ知らせる、といった用途が考えられる
（その場合も、順位の自動変更・安全性の判定にはしない）。

## 4. 候補避難所地点のハザード判定

### 実装していたこと

候補1〜3の避難所の地点が、ハザード区域の内部または境界上にあるかを判定し、`candidate_N_shelter_in_hazard` /
`candidate_N_shelter_hazard_types` としてCSVへ、候補表の「避難所地点のハザード」としてレビュー画面へ出していた。
避難所ごとの判定は結果を使い回して処理時間を抑えていた。

### 技術的に動作確認できていたこと

* 公式ハザードデータ5ZIP（合計106,007 Polygon）で、津波・高潮・洪水・土砂災害の判定がColabで最後まで完走
* 複数種別への重複該当、区域外、座標欠損の各ケースの判定が、実データ相当のCSVで想定どおりであること
* 不正なPolygon（自己交差等）を `make_valid()` で直したとき、避難所地点の判定が3件変わることの確認
  （[docs/hazard-data.md](../hazard-data.md) の「ジオメトリの扱い」）

### なぜ v1.1.0 で外したか

担当部署が確認したいのは、避難所や経路ではなく **本人住所がハザード区域内にあるか** であるため。避難所側のハザードは
業務判断に使わず、CSVの列数を増やして見づらくしていた。なお、ハザードの読み込み・正規化の処理自体は、本人住所の
判定に引き続き使っている。

### 将来の再利用の可能性

避難所の立地リスクを一覧にする、避難所の見直し検討の資料にする、といった用途。ただし候補の自動除外・順位変更に
使う場合は、要件の確認が別途必要（v1.0.0 から「ハザードによる候補の自動除外は行わない」方針）。

## 5. 本人→候補直線のハザード交差判定

### 実装していたこと

本人の地点と候補避難所を結ぶ単純な直線（`LineString`）がハザード区域と交差するかを判定し、
`candidate_N_straight_line_intersects_hazard` / `candidate_N_straight_line_hazard_types` としてCSVへ、
「本人と避難所の間のハザード区域（参考）」としてレビュー画面へ出していた。道路上の避難経路の判定ではなく、
画面でもそのように注記していた。

### 技術的に動作確認できていたこと

候補避難所地点の判定と同じ実データ・テストで確認（空間インデックスで交差し得るポリゴンに絞ってから判定）。

### なぜ v1.1.0 で外したか

実際にどの経路を使うかは職員が本人への聞き取り等で判断するため、直線上のハザードは業務判断に使わない。
v1.1.0 のレビュー画面の直線は、本人と候補避難所の位置関係と距離を見るためだけに引くもので、実際に通る経路では
ないことを画面に明示している。

### 将来の再利用の可能性

経路が確定した後に、その経路（道路経路・聞き取りで決めた経路）とハザード区域の重なりを確認する用途。
その場合は直線ではなく、確定した経路そのものを対象にする必要がある。

## 6. 避難所の災害種別対応情報

### 実装していたこと

BODIKの避難所データの `災害種別_` で始まる列（洪水・津波など。値は `1`=対応済み / `2`=2階以上であれば対応済み /
空欄=未対応）を、避難所ごとに保持し、`candidate_N_disaster_support` としてCSVへ、候補表の「災害種別対応」
（○ 対応 / △ 2階以上 / × 非対応）としてレビュー画面へ出していた。距離順位・候補の除外には使わなかった。

### 技術的に動作確認できていたこと

* 自治体標準ODSの列名（`災害種別_洪水` 等）を、特定の種別名に固定せず動的に認識すること
* 想定外のコード値を「対応」と推測せず、値を保持して要確認と表示すること
* 実際のBODIK避難所データとの組み合わせで、Colabで完走すること

### なぜ v1.1.0 で外したか

担当部署から、避難所がどの災害種別に対応しているかは今回の成果物には不要との意見があったため。候補算出に必要なのは
避難所の **名称・緯度・経度** だけである。BODIKの元データに `災害種別_` 列が存在すること自体は問題なく、単に使わない。
BODIKからの避難所一覧の取得の仕組み（API取得・CSVフォールバック・列名の正規化・座標チェック）は維持している。

### 将来の再利用の可能性

避難所の対応状況を踏まえた避難先の検討資料が必要になった場合（例: 津波の想定がある地域で、津波に対応した避難所を
絞り込む）。この場合も、対応状況による候補の自動除外・順位変更をするかどうかは、要件の確認が別途必要。
