## 2. sheltermatch の目的

**要支援者本人の住所についてハザードの影響を確認し、直線距離が近い避難所候補を職員へ提示する** こと。
担当部署の実運用レビューで確認できた業務要件は次のとおり。

1. 必要なのは、避難所までの **直線距離**
2. 実際にどの経路を使うかは、本人への聞き取り等によって職員が判断する
3. ハザードについて確認したいのは、避難所や経路ではなく **本人住所がハザード区域内にあるか**
4. 集計情報として、各ハザード区域内に何人の住所があるかを確認したい
5. 結果CSVは情報が多すぎる
6. 避難所がどの災害種別に対応しているかは、今回の成果物には不要

これに合わせて、`sheltermatch` が整理して提示するのは次の4点である。

1. 要支援者本人の位置と、本人住所のハザード（ハザード区域の内部または境界上にあるか）
2. 距離が近い避難所候補1〜3
3. 候補ごとの、本人住所からの直線距離
4. ハザードの大分類ごとの、住所が該当する人数

**行わないこと**: 避難所・経路の安全性の評価、避難経路の自動決定、ハザードによる候補の除外、危険度のスコア化、
避難所の推薦。候補の順位は本人住所→避難所の直線距離だけで決める。

最終的な避難所の決定と、実際に使う経路の判断は職員が行う。

## 3. 完成範囲の整理

sheltermatch本体の主要機能は、完成しているものとして扱う。

本体の目的は、**要支援者本人の住所のハザードと、直線距離が近い避難所候補を、職員が判断するために整理して
提示すること** である。正式なデータ成果物は `assigned_shelters.csv`（14列）である。

以下は、本体の完成条件には含めない。ただし「完成条件に含めない」ことは「実装しない・不要」という意味では

## 4. 本体として完成させる機能

### 4.1 要支援者データの読込

要支援者一覧CSV（`resident_id,address,latitude,longitude,geocode_status` の5列）を読み込む。

座標が欠損している行や不正な行も削除せず、入力した値も書き換えずに処理結果へ残す。座標が利用できない場合は
候補計算を行わず、`match_status`（`no_coordinates` / `invalid_coordinates`）で状態を明示する。

### 4.2 避難所データの取得

避難所一覧は、原則としてBODIK Data APIから糸満市の自治体標準オープンデータセットを取得する。
API取得に失敗した場合はCSVアップロードへフォールバックできる。

候補の算出に使うのは、**名称・緯度・経度** の3列だけである（自治体標準ODSの日本語列名 `名称` / `緯度` / `経度` を
内部標準列名 `name` / `latitude` / `longitude` へ正規化する）。座標が使えない避難所は距離計算の対象から除く。
BODIKの元データにある `災害種別_` で始まる列などは、存在していても読み捨てる（変換・保持・出力・画面表示をしない）。

### 4.3 避難所候補の算出

要支援者と各避難所の座標から `geopy.distance.geodesic` により直線距離を計算し、距離が近い上位 **3件** を候補
（`candidate_1`〜`candidate_3` / `distance_1_m`〜`distance_3_m`）として出力する。候補数は正式仕様として3件固定で、
利用者設定（旧 `TOP_N`）では変えられない。これは道路距離・避難経路ではない。

**候補順位は直線距離だけで決める。** 距離が同じ場合は避難所名で順序を安定させる。以下によって順位を変えない。

* 避難所のハザード
* 避難所の災害種別対応
* 道路距離
* その他の独自スコア

### 4.4 ハザード区域判定（本人住所）

ハザード区域判定は **sheltermatch本体の完成対象** である。判定する対象は **要支援者本人の地点だけ** である
（v1.1.0〜。候補避難所の地点・本人と避難所を結ぶ直線・道路経路は判定しない）。

実行時には `ENABLE_HAZARD_CHECK` によって使用するか選択できるが、これは利用時の任意設定であり、開発上の
優先度が低いことを意味しない。ハザード判定をしない場合、結果CSVのハザード列（`resident_in_hazard` /
`resident_hazard_types`）は空欄になる（「区域外」ではなく「判定していない」）。

読み込んだGeoJSON / ShapefileをEPSG:4326のPolygon / MultiPolygonとして統合し、本人の地点がハザード区域の
内部または境界上にあるかを判定する。「安全な避難経路」とは表現しない。

有効なPolygon / MultiPolygonは一切変更せずそのまま使う。公式配布データに実際に含まれている `is_valid=False`
のPolygon / MultiPolygon（自己交差等）は `shapely.make_valid()` で直してから使う（GeometryCollectionに
なる場合はPolygon / MultiPolygon成分だけを使い、区域として使える形にならなかったものは判定対象外とする）。
空・欠損のジオメトリ、Polygon / MultiPolygon以外のジオメトリは判定対象外とする。直した行も元の
`hazard_type` をそのまま引き継ぎ、種別・カテゴリを再解釈しない。

**ハザードの大分類と詳細区分**: 読み込んだ区域には、大分類 `hazard_category`（津波・高潮・洪水・土砂災害など。
アップロードしたファイルの判定結果から決まる）と、詳細区分つきの `hazard_type` を持たせる。大分類は
全体の集計に、詳細区分は個人の詳細表示（`resident_hazard_types`・レビュー画面）にだけ使う。

対応対象としているハザード種別と、その詳細区分の保持状況は以下のとおり。

* 洪水（国土数値情報A31a）: 大分類は「洪水」。河川区分（洪水予報河川・水位周知河川 / その他の河川）と、ZIP内部の
  サブフォルダのカテゴリを詳細区分として保持する（実データで確認済みのカテゴリは `10_計画規模` /
  `20_想定最大規模` / `30_浸水継続時間` / `41_家屋倒壊等氾濫想定区域_氾濫流` / `42_家屋倒壊等氾濫想定区域_河岸侵食`）
* 土砂災害（国土数値情報A33）: 大分類は「土砂災害」。ファイル名から入力なしで自動判定し、公式属性 `A33_001`（現象の
  種類）/ `A33_002`（区域区分）から `急傾斜地の崩壊` / `土石流` / `地滑り` と、`土砂災害警戒区域(指定済)` /
  `土砂災害特別警戒区域(指定済)` 等の詳細区分をそのまま保持する
* 津波（沖縄県LEVEL1〜7）: 大分類は「津波」。実データの `分類` 属性（例: `0.01m以上0.3m未満`）を保持する
* 高潮（沖縄県）: 大分類は「高潮」。ファイル名からカテゴリ（`最大浸水深` / `浸水継続時間`）を保持する

複数種類に該当する場合は、該当種別をすべて保持する。ハザード判定結果による候補の自動除外・自動順位変更は
行わない。

**ハザード別の人数集計**: 本人住所について、ハザードの大分類ごとに該当する人数を集計する（Notebookの結果表示と
レビュー画面の上部）。判定時に付けた大分類（構造化された値）を使い、表示用の文字列を後から解析して数えることは
しない。数え方は次のとおり（詳細は [docs/hazard-data.md](./hazard-data.md) の「9」）。

* 人 × 大分類で重複を除く。同じ大分類の複数ポリゴンに該当しても、その大分類は1人
* 複数の大分類に該当する人は、該当する大分類それぞれに1人ずつ計上する（各分類の合計は「いずれかに該当」と
  一致しない場合がある）
* 「いずれかに該当」は、1つ以上の大分類に該当した人を重複なしで数える
* 「ハザード該当なし」は、有効な座標があり、判定した結果どの大分類にも該当しなかった人。**座標未取得の人は含めず**、
  別に「座標未取得」として数える

詳細なデータ取得・利用手順は [docs/hazard-data.md](./hazard-data.md) を参照。

### 4.5 結果CSV（`assigned_shelters.csv`）

正式な出力列は次の14列で、この順に並べる。

```text
resident_id, address, latitude, longitude, geocode_status, match_status,
resident_in_hazard, resident_hazard_types,
candidate_1, distance_1_m, candidate_2, distance_2_m, candidate_3, distance_3_m
```

* 入力CSVにほかの列（独自の備考列など）があれば、この14列の後ろにそのまま残す（入力情報を黙って消さない）
* 前回の結果CSV（v1.0.0 の旧列を含む）を再投入した場合は、このツールが作る列（旧版の `candidate_N_disaster_support`・
  `candidate_N_shelter_*`・`candidate_N_straight_line_*` を含む）だけを今回の結果で置き換える。`candidate_1_備考` の
  ような職員の追加列は、名前が似ていても残す
* 座標が使えない行は、行を削除せず、`resident_id`・`address` 等の入力値を残し、`match_status` に理由を残し、
  ハザード列・候補・距離は空欄にする。曖昧な座標・近い住所・代表点による補完はしない
* v1.0.0 の出力にあった `candidate_N_disaster_support` / `candidate_N_shelter_in_hazard` /
  `candidate_N_shelter_hazard_types` / `candidate_N_straight_line_intersects_hazard` /
  `candidate_N_straight_line_hazard_types` は出力しない

## 5. 住所→座標変換の位置付け

住所→座標変換は **sheltermatch本体処理の前処理** であり、独立Notebook `address_geocode.ipynb` として
実装済みである（本体へは統合しない）。本体の完成は、この機能に依存させない。緯度・経度があらかじめ用意された
要支援者データで、候補算出・本人住所のハザード判定・結果CSV出力まで完走できる。

### 現在の方式: ABR公式CSVの手動取得・直接照合

* 公式ABR CSV（地番住所用: 町字マスタ・地番マスタ・地番位置参照の3種類、住居表示住所用: 住居表示-街区・
  街区位置参照・住居・住居位置参照の4種類）を利用者が手動アップロードし、対象自治体（`lg_code=472107`）の
  データを抽出・結合して、pandasで直接照合する（自動ダウンロードは行わない）。種別はファイル名ではなく
  CSVの列構成で判定し、沖縄県単位で配布される住居表示データも `lg_code` で糸満市分だけを使う
* 地番住所は町字＋地番（1〜3段）の完全一致、住居表示住所（`rsdt_addr_flg=1`の町字）は町字＋街区符号＋
  住居番号（＋住居番号2）の完全一致で照合する。住居表示住所の座標は住居位置参照からだけ取り、街区だけの
  一致では座標を付けない（街区位置参照の代表点で代用しない）。3段の番号（例: `36番7-201号`）は3段の完全一致を
  最優先し、空白区切りの方書を除外した住所で3段の完全一致が0件の場合だけ、3段目を除いた住居がABRに一意にあり
  座標もある等の条件を満たすときに限り、3段目を部屋番号等として除外する（方書の無い3段の住所では除外しない）
* 施設名・建物名・部屋番号等の方書は、住所全文で見つからない場合だけ、元の住所の空白の位置で後ろを外して
  照合し直す（空白の無い住所は切り詰めない）。`address` 列は入力のまま出力する
* 出力CSVは本体の要支援者CSVと同じ5列で、そのまま本体へ投入できる
* ABRマスター準備と住所CSV変換を分離しており、同じColabランタイムの間は、住所CSVを差し替えるたびに
  ABR ZIPを再アップロードする必要はない
* 曖昧な住所を推測して `matched` 扱いにしない。住居表示データが不完全・不整合（住居と住居位置参照のキーが
  一意でない等）な場合は、曖昧な座標を作らずに処理を止める

住所表記の揺れ（全角／半角、漢数字の丁目、ハイフン類、空白、「字」「大字」の有無、`番地`/`番`/`号`/`の`
の表記差）・住居表示住所・方書付き住所への対応と、別の住所を同一視していないこと、県単位データから対象
自治体だけを使うことは、架空のABRデータを使った `test/test_address_conversion.py` で回帰テストしている。
実際のABRデータと実際の運用住所データによるGoogle Colabでの確認（2026-09-29）では、1,061件中1,024件を変換した
（「7.2」）。変換できなかった住所は、推測で補完せずに未変換として残す（100%の自動変換を目標にして照合の条件を
緩めない）。ABRデータの更新時は、住所CSVを再変換して件数を比較する（手順は
[docs/address-data.md](./address-data.md) の「10. データの更新と再変換の手順」）。

### この方式を選んだ理由（判断根拠）

JageocoderとABR Geocoder（`@digital-go-jp/abr-geocoder`、および `abrdb`/`abrg` 構成）は、いずれも辞書・
キャッシュ生成のために配布データを自動ダウンロードする構成で、Google Colab・GitHub-hosted runner等の
クラウド環境から配布データを取得する段階で403等のエラーが発生した（ABR Geocoder公式リポジトリでも既知の
外部要因として報告されている。Jageocoderには加えてPython・converter APIの互換性問題もあった）。
そのため、利用者がABR公式CSVを手動取得して直接照合する方式（`experiments/abr_csv_geocode_poc.ipynb` で検証）
を採用した。検証の記録は `experiments/` に残している。

他自治体への展開は、必要になった場合に追加データ・追加検証を検討する。

データ取得元・利用手順・`geocode_status` の詳細は [docs/address-data.md](./address-data.md) を参照。

## 6. 現時点で実装済みの主要機能

### 6.1 Notebook本体（`sheltermatch.ipynb`）

* 要支援者CSV読込（UTF-8 / CP932の自動判定、5列・`resident_id` の空欄・重複チェック）
* 座標の欠損（`no_coordinates`）と、値はあるが使えない（`invalid_coordinates`）の区別。該当行も削除せず、
  入力値を書き換えずに結果へ保持
* BODIK Data APIからの避難所取得、API失敗時のCSVフォールバック、自治体標準ODS列名（名称・緯度・経度）の正規化。
  使うのは名称・緯度・経度だけ
* geodesicによる直線距離計算と上位3候補の算出
* ハザードデータの読込（GeoJSON単体、GeoJSON / Shapefileを含むZIP。展開・変換不要。大文字の拡張子、
  ZIP内パストラバーサル対策、CP932ファイル名の文字化け復元、CRSのWGS84統一、不正Polygonの修復）と、
  洪水・土砂災害・津波・高潮の種別・大分類・詳細区分の自動判定
* 要支援者本人の地点のハザード判定（空間インデックスで絞り込んでから判定）と、ハザード大分類別の人数集計
* UTF-8 BOM付き結果CSV（`assigned_shelters.csv`。正式な14列）の出力
* レビュー用HTML（`sheltermatch_review.zip`）の出力（下記「6.3」）
* 誤った結果を出さないための停止・無効化: ハザードデータ未読込のまま候補算出セルを実行した場合の停止、
  入力の読み直しに失敗した場合や設定・入力のセルを再実行した場合の前回結果の無効化、
  前回の結果CSVを再投入した場合の結果列の置き換え

Notebookの利用者設定は、自治体の設定名 `CONFIG_NAME` と、Notebookの既定値である `ENABLE_HAZARD_CHECK`・
`SHELTER_SOURCE` だけである（旧 `TOP_N`・`ENABLE_ROAD_ROUTES` は廃止）。自治体名・BODIKのresource_id・通常使う設定は
`configs/<CONFIG_NAME>.json`（糸満市は `itoman-city.json`）にまとめ、設定ファイルに値があればそちらを優先し、
項目が無ければNotebookの既定値を使う。設定ファイルを取得・解釈できない場合は、既定値で続行せず止まる
（[configs/README.md](../configs/README.md)）。
Notebookは osmnx を導入せず、OpenStreetMap の道路データも取得しない。

結果CSVの出力セルは、レビューHTMLの出力より前にある。レビューHTMLの作成に失敗しても、正式成果物である結果CSVは
失われない。

### 6.3 レビュー用HTML（補助成果物）

`assigned_shelters.csv` が正式なデータ成果物である。レビュー用HTML（`sheltermatch_review.zip` を展開した
`review.html`）は、**正式な割り当て結果ではなく、CSVの結果を職員が地図上で目視確認するための補助成果物**
である。

**オフライン利用と作り方**

* 地図ライブラリ（Leaflet。バージョン固定・SHA-256確認・LICENSE同梱）、背景地図PNG（国土地理院の地理院タイルを
  Notebook実行時に必要範囲だけ取得して画像化）、ハザード区域PNG（大分類ごと）をすべて同梱し、
  展開したフォルダだけで **外部通信なしに** 開ける。出典は地図下部に表示する
* HTMLは1ファイルで、全要支援者のデータをJSONとして埋め込み、画面には選択した1人だけを描く
* 候補の順位・距離・本人のハザード・集計は候補算出で得たものをそのまま使い、生成時にCSVおよび要支援者ごとの
  データとの一致を確認する（食い違う場合はHTMLを作らずに停止する）
* 背景地図の取得に失敗した場合はZIPを作らない（結果CSVは出力済みのため影響しない）

**画面上部: ハザード別の人数集計**

* 総件数・座標あり・座標未取得・いずれかに該当・ハザード該当なし・ハザード大分類別の人数を表示する
* 「同じ人が複数のハザードに該当する場合は、それぞれに1件ずつ計上しています。各大分類の人数を合計しても『いずれかに
  該当』とは一致しない場合があります」と、座標未取得の人は「ハザード該当なし」に含めないことを画面に表示する
* 「集計をたたむ」で隠せる。ハザード判定を実施していない場合は、件数のみ表示する

**要支援者一覧（多数件のレビュー）**

* resident_id・住所での検索
* 既存データの事実だけによる絞り込み: 「座標を確認」（`match_status` が `ok` 以外）、「ハザード該当あり」
  （本人住所がいずれかのハザードに該当。ハザード判定を実施した場合だけ）。複数の絞り込みと検索はAND条件
* 絞り込みは **安全・危険・優先度の自動評価ではない**。該当0件のときは前の要支援者の表示（地図・ハザード区域を
  含む）を残さない
* 一覧は一度に50件までを描き、前へ／次へで順に確認できる
* 内部の状態名（`match_status: ok` 等）は表示せず、座標が無い・不正な場合だけ職員向けの日本語で示す

**個人表示（要支援者を選択したとき）**

* 本人地点、本人住所のハザード（大分類と詳細区分。該当なし・判定できません〈座標なし〉・判定していません〈ハザード判定
  未実施〉を区別して表示）、候補1〜3と直線距離を表示する。地図には、本人地点・候補避難所1〜3・本人→候補の直線・
  ハザード区域を描く
* 候補との線は **直線** として表示し、実際に通る経路ではないことを画面に明示する（避難経路と誤認させる表現を使わない）
* 候補表は、順位・避難所名・直線距離の3列。Tab / Shift+Tab で行を移動し、Enter・Space で候補を選べる
  （選ぶとその候補の直線と避難所名を強調する）
* 「全候補を表示」で、本人と候補1〜3の位置関係へ戻せる。候補詳細（候補表・注記）は折りたたみ、地図を広く使える
* 画面上部には「避難所候補は直線距離による候補であり、最終的な割り当てではない」と、「地図の線は実際に通る経路では
  ない」を常に表示する

**画面から削除した情報（v1.0.0 にあったもの）**: 道路に沿った参考経路・道路上の距離・道路経路の選択UI・道路経路算出
不可の表示と絞り込み、候補避難所地点のハザード、本人→候補の直線交差ハザード、避難所の災害種別対応。

### 6.4 Notebook外へ切り出した実装

Notebookが「利用者が上から順に実行する手順」として読めるよう、実装の詳細は通常のPython / HTMLファイルとして
保守し、Notebook側には職員が実際に行う操作（設定・アップロード・結果と処理時間の表示）だけを残す。

| ファイル | 内容 | Notebookから呼ぶ入口 | API互換性の値 |
| --- | --- | --- | --- |
| `src/hazard/hazard_loader.py` | ハザードデータ（GeoJSON / Shapefile / 公式配布ZIP）の読込・正規化・統合。大分類 `hazard_category` と詳細区分 `hazard_type` を付ける | `load_uploaded_hazards()` | `HAZARD_LOADER_API_VERSION` = 2 |
| `src/assignment/shelter_assignment.py` | 避難所候補1〜3（直線距離）の算出、本人住所のハザード判定、ハザード大分類別の人数集計、結果CSV（14列）の組み立て | `build_assignment()` / `summarize_hazards()` | `ASSIGNMENT_API_VERSION` = 1 |
| `src/review/review_builder.py` | レビュー成果物の生成（地図素材の準備・ハザードPNG・データ組み立てとCSV・集計の照合・ZIP出力） | `build_review_package()` | `REVIEW_BUILDER_API_VERSION` = 3 |
| `src/review/review_template.html` | `review.html` の画面（HTML / CSS / JavaScript） | （テンプレートとして読み込む） | — |
| `src/config/municipality_config.py` | 自治体ごとの設定ファイル（`configs/<CONFIG_NAME>.json`）の読込・検証、Notebook既定値との合成 | `load_config()` / `resolve_setting()` | `CONFIG_LOADER_API_VERSION` = 1 |

`sheltermatch.ipynb` は、Google Colab実行時にこれらのファイルと自治体の設定ファイル（`configs/<CONFIG_NAME>.json`）を
GitHubの指定した版（現在は `v1.2.0` タグ）から取得し、`importlib` でモジュールとして読み込む（取得したコードを
`exec()` で直接実行はしない）。外部モジュールは「外部モジュール準備」セルで取得し、設定ファイルは続く「設定ファイル読込」
セルで取得する。各モジュールのAPI互換性の値がNotebook側の期待値と一致することを確認してから処理を進める
（互換性のない組み合わせのまま処理を続けない）。設定ファイルを取得・解釈できない場合も、Notebookの既定値で続行せず止まる。

**取得する版（外部モジュールと設定ファイルの版の固定）**: 通常運用の `sheltermatch.ipynb` と `address_geocode.ipynb` は、
`src/` と `configs/` を `v1.2.0` タグから取得する。`SHELTERMATCH_CODE_REF = "v1.2.0"` から取得元
（`GITHUB_RAW_REPO_URL`・`GITHUB_RAW_BASE_URL`）を組み立て、上表のファイルと設定ファイルをすべてこの1つの取得元から
取得する。`main` とタグを混在させない。実行時には「外部モジュール: v1.2.0」と取得元のURLを表示し、取得できなかった
場合は、取得対象の版・URL・通信エラーの内容を表示して止まる。

固定したのは、Notebookが実行時に取得する `src/` と `configs/` の版である。`sheltermatch.ipynb` 自体は `main` 上の
ファイルで、今後も `main` で更新され得る。Notebookと取得した `src/` の組み合わせは、上表のAPI互換性の値で確認する
（一致しなければ止まる）。`experiments/gsi_shelter_compare/` の比較実験は通常の業務Notebookとは別で、`main` の比較ロジック・
設定を取得する（タグには固定しない）。

**リリースの経緯と現在の状態**

* `v1.0.0`: 運用開始（2026-09-29 に実データで一気通貫の確認。「7.2」）。付け直したり削除したりしない。

  そのタグ内の `sheltermatch.ipynb` は `SHELTERMATCH_CODE_REF = "v1.0.0"` のため、タグ内で自己整合しておらず、
  `configs/` も含まない。このタグは今後変更しない（付け直さない・削除しない）。通常運用・配布の対象にはしない。
* `v1.2.0`: v1.1.0 の業務要件を維持したうえで、自治体設定JSON（`configs/itoman-city.json`）、設定読込・検証

今後の更新方針:

* `main` へ変更を取り込んでも、それだけでは運用のNotebookが取得する外部モジュール・設定ファイルは変わらない
* 新しい版を運用へ反映するときは、動作確認をしてから、取得する版（`SHELTERMATCH_CODE_REF`）を明示的に更新する
* 取得する版の更新は、意図したバージョン更新として Pull Request で行い、タグは新しい版名で新規に作成する

モジュールはNotebookのグローバル変数には依存せず、必要なデータはすべて引数で受け取る。

通常のNotebook運用では、GitHubやBODIK・地理院タイル・Leaflet等への外部通信は、Google Colabでの処理実行時に
発生する（OpenStreetMap等の道路データは取得しない）。生成済みの `sheltermatch_review.zip` は、必要な素材を同梱して
いるため外部通信なしで利用できる。

## 7. 確認・テストの体制

自動テスト（CI）と実機確認は役割が異なる。CIが成功していることは、Google Colab・実データでの動作確認に
代わるものではない。

| 確認の種類 | 対象 | 使うデータ |
| --- | --- | --- |
| 自動テスト（CI） | 住所変換、候補算出・本人住所のハザード判定・ハザード大分類別の集計・結果CSVの列、レビューHTMLの内容、Notebookの通し実行（`src/` は作業ツリーのものを使用）、Notebookの外部モジュールの取得先 | リポジトリ内の完全な架空データ（外部データを取得しない） |
| 開発環境での検証 | `file://` で開いたレビュー画面のブラウザでの確認 | 架空の要支援者・避難所・ハザード区域 |
| 実機確認 | Google Colabでの実行、実際のBODIK・公式ハザードデータ・ABRデータ、生成したレビュー画面の確認 | 実際の公開データと実際の運用データ（実データはリポジトリへ含めない） |

### 7.1 自動テストとCI

* ローカル: `python3 -m unittest discover -s test`（必要なライブラリは `test/requirements.txt`）
* GitHub Actions（`.github/workflows/ci.yml`）: `main` 向けの Pull Request、`main` への push、`workflow_dispatch`
  で、同じテスト（`python -m unittest discover -s test`）を Python 3.12 で実行する
* CIでは依存ライブラリが import できることを確認してから、外部へ接続できない状態でテストを実行し、skip が
  1件でもあれば失敗とする。外部のハザード・避難所データは取得しない
* v1.2.0（2026-10-03時点）で、テストは249件（住所変換・候補算出と本人住所のハザード判定・集計・結果CSV・ハザード読込・
  レビューHTML・Notebookの通し実行・外部モジュールの取得先・自治体設定ファイル・比較実験）。外部へ接続できない状態で、
  すべて成功し skip 0件であることを確認している（v1.1.0 候補の 2026-10-01 時点は152件、v1.0.0 時点は107件。
  道路経路のテスト20件は、機能の削除とともに削除した）

詳細は [test/README.md](../test/README.md) を参照。

### 7.2 実機確認の実績

以下は **v1.0.0 時点の確認実績** である（記録として残す。v1.1.0 で通常運用から外した機能の確認を含む）。
v1.2.0 の Google Colab での確認は、リリース手順（「6.4」）の手順5〜8（`v1.2.0` タグの作成後）で行う（「7.3」）。

**実データによる一気通貫の確認（Google Colab、2026-09-29、v1.0.0）**

実際のABRデータと実際の運用住所データを使い、次の流れを Google Colab で通して実行した。

```text
address_geocode.ipynb（住所変換）
  ↓ 変換後のCSVをそのまま投入
```

## 8. 今後の優先順位

住所変換・本体・レビュー画面・CIは、現在の目的（担当部署の業務要件）に必要な範囲で整っている。v1.0.0 は実データでの
確認も済んで運用の段階に入っており、v1.2.0 は、`v1.2.0` タグの作成と Google Colab での実機確認を経て運用へ反映する（未配布。「6.4」）。
今後は、機能追加よりも次を優先する。

1. **依頼部署からの利用フィードバック**
   * 結果CSV・レビューHTMLが、職員の判断資料として理解しやすいか
2. **運用上の不具合への対応**
   * 実利用で発生した操作上の問題・通常業務上の不具合の修正
   * `src/` の修正は、`main` へ取り込むだけでは運用に反映されない。動作確認をしてから、取得する版
     （`SHELTERMATCH_CODE_REF`）を Pull Request で更新し、新しい版名のタグを作成する（「6.4」の今後の更新方針）
3. **ABR等の公開データ更新時の再確認**
   * ABRデータの更新時は、住所CSVを再変換して件数を前回と比較し、成果物を作り直す（手順は
     [docs/address-data.md](./address-data.md) の「10. データの更新と再変換の手順」）
   * 避難所（BODIK）・ハザードの各データも、更新を確認した際に成果物を作り直す
4. **必要になった場合のみ追加改善**
   * 事前確認で挙げた未対応の事項（追加列の値の扱い、誤った座標の警告等）は、判断に応じて対応する
     （[docs/pre-production-check-2026-09-28.md](./pre-production-check-2026-09-28.md)）
   * 追加の性能最適化は、実測して問題があった場合だけ行う（ハザード判定の空間インデックス化は実施済み）
   * 住所変換の未変換を減らす目的で、照合の条件を緩めることはしない

**過去の技術検証（v1.0.0）の再利用**

道路経路・避難所側のハザード等は、現行の改善候補ではない。別の業務要件が出た場合に、
[docs/notes/v1.0.0-extended-features.md](./notes/v1.0.0-extended-features.md) の「将来の再利用の可能性」を参考に、
`v1.0.0` タグの実装を出発点として検討する。

## 9. 開発時のガードレール

今後の開発・レビューでは以下を守る。

### 成果物の位置付けを変えない

* `assigned_shelters.csv` が正式なデータ成果物である
* レビューHTMLは、職員の目視確認を支援する補助成果物である
* 候補順位は本人住所→避難所の直線距離から変更しない。ハザード情報・避難所の災害種別等による自動順位変更・自動除外を
  しない
* 避難所・経路の安全性の評価、避難経路の自動決定、避難所の自動推薦をしない。地図の線は直線であり、実際に通る経路
  ではない。実際の経路は職員が本人への聞き取り等で判断する
* 「安全」「危険」「推奨」といった総合判定・独自の危険度スコアを生成しない。表示・絞り込みは既存データの事実
  だけで行う

### 本体機能と前処理・任意機能を混同しない

* 住所→座標変換で問題が発生しても、距離計算・ハザード判定等の本体開発を止めない
* `ENABLE_HAZARD_CHECK` のような実行時ON/OFF設定は、利用者がその処理を実行するか選択するためのもので、その機能が
  完成対象外・不要であることを意味しない
* 実装済みの機能を、開発者・生成AIが独自判断で「本体外だから不要」と削らない。機能を外すのは、v1.1.0 のように、
  担当部署の業務要件で必要性がないと確認できた場合に限る。その場合も、外した機能の内容・確認できていたこと・外した
  理由を note に記録し、実装は版（タグ）に残す（「6.2」）

### 技術的に難しいことを理由に要件を勝手に縮小しない

実装・検証で問題が見つかった場合は、

1. 問題を具体的に整理する
2. 本体要件か補助機能かを確認する
3. 本体要件なら解決方法を検討する
4. 本体要件を外す必要がある場合は、利用者の判断を仰ぐ

の順とする。開発者・生成AIが独自判断で「難しいため後回し」「PoCなので不要」と要件を変更しない。

### 機能を増やしすぎない・複雑にしすぎない

* 新機能は、実利用上の必要性を確認してから追加する
* 通常業務で問題にならない極端な異常ケースへの過剰対応で、コードを複雑化しない
* 業務要件にない情報（ハザードのリスクスコア・避難所の自動推薦・安全経路判定・新しい外部API・新しいGIS分析など）を
  追加しない。必要な情報を減らし、判断しやすくすることを優先する

### 個人情報を扱う

* 実際の要支援者データ・住所データを、GitHub・テストデータ・ドキュメントへ含めない（サンプルは完全な架空データ
  とする）
* 要支援者の情報を外部のAPI等へ送らない（現在、要支援者の情報を外部へ送る処理はない）

### 最終目的を維持する

このプロジェクトのゴールは、個々のライブラリやジオコーダーを動かすことではない。

**要支援者本人の住所のハザードと、直線距離が近い避難所候補を、職員が避難先を判断するために整理して提示すること**
がゴールである。個別技術の問題に開発全体を引っ張られない。
